# G28 — v0.1.5 Product Readiness Foundation

- Status: Complete — candidate evidence accepted; not released or UAT-complete
- Type: Release-candidate implementation goal; not an alpha declaration
- Depends on: G26 implementation evidence, the accepted G27 contract package,
  S27-EVAL, S27-ROLE, S27-CREATE, and the existing G18/G20 boundaries
- Unblocks: G27 runtime implementation, G24 final human UAT, and G25 alpha
  readiness review

## Outcome

G28 produces a useful v0.1.5 candidate before human UAT. It implements the
evaluation foundation, central role registry, and browser-first setup/create
path required to evaluate GigAI as a product rather than merely as plumbing.

The candidate must make this ordinary flow work after normal project setup:

```text
gigai setup
gigai create tailor-resume-for-job
```

The command opens the local HTMX flow, uses a truthful configured model path,
asks the operator for the Gig definition, and routes later discovery/build
behavior through the existing authority boundaries.

G28 does not declare alpha or public release. G25 retains that decision.

## Contract gate

Before implementation, the three spikes must be accepted:

- [S27-EVAL](S27-EVAL-evaluation-foundation.md), with its [decision
  record](../../evidence/phase-5/S27-EVAL/decision-record.md);
- [S27-ROLE](S27-ROLE-central-role-registry.md), with its [decision
  record](../../evidence/phase-5/S27-ROLE/decision-record.md); and
- [S27-CREATE](S27-CREATE-browser-first-create-and-model-setup.md), with its
  [decision record](../../evidence/phase-5/S27-CREATE/decision-record.md).

Each spike must state whether a schema/resource amendment is needed. Any
amendment must preserve existing authority, hashes, and installed replay
unless explicitly accepted as an additive contract change.

G28 must also preserve:

- G18 provider and credential boundaries;
- G20 evidence and quality gates;
- G22 loopback/session authority;
- G26 builder-session and proposal lifecycle authority; and
- G27's accepted discovery-manifest contract.

## First implementation boundary

1. Add explicit test-tier commands and reporting without moving behavioral evals
   into ordinary unit-test pass/fail claims.
2. Implement the accepted evaluator/corpus manifest and first G26/G27 eval
   suites, including deliberate negative cases.
3. Implement the accepted namespaced role registry and compatibility path for
   existing serialized role strings.
4. Connect setup to truthful model choice and readiness.
5. Make `gigai create <gig-name>` open HTMX after normal setup without
   implementation-facing flags.
6. Prove the installed v0.1.5 candidate before G24 begins human UAT.

## In scope

- evaluation taxonomy, registry, reports, corpus splits, and first product
  behavioral evals;
- unit/integration/installed-E2E command separation;
- central role registry and structured role references;
- setup model selection, credential-reference presentation, and readiness;
- browser-first create entry point and plain-language initial flow;
- integration and installed-E2E coverage for the target command; and
- release-candidate evidence for v0.1.5.

## Out of scope

- alpha/public release declaration;
- arbitrary Codex/Claude adapter support without accepted evidence;
- autonomous web research;
- target mutation or Run execution during creation;
- redesigning G20 or S16-EVAL authority; and
- human UAT itself, which consumes the v0.1.5 candidate through G24.

## State and authority contract

1. Eval reports describe evidence; they cannot approve a Gig or change runtime
   authority.
2. A role reference selects a registered purpose; it does not grant a
   capability or permission.
3. Setup records model selection and readiness without storing credential
   values.
4. `gigai create <gig-name>` opens a browser session, but browser/model state
   remains a disposable projection over durable session records.
5. No model, role, eval, or setup response creates a proposal, Run, target
   effect, or active-version transition without the existing explicit lifecycle.
6. Existing persisted role strings remain readable only through an explicit
   compatibility path; they are not silently reinterpreted.

## Acceptance criteria

1. S27-EVAL, S27-ROLE, and S27-CREATE decision records are accepted and cited.
2. Four test/eval tiers have separate commands, reports, and CI cadence.
3. The first G26/G27 behavioral eval suites have labeled cases, negative
   fixtures, fixed splits, bars, and sanitized reports.
4. Plumbing-only results are structurally distinct from candidate behavior
   scores.
5. Built-in and extensible roles are centrally registered, namespaced,
   versioned, and validated at new authority boundaries.
6. Existing role-bearing records replay through an explicit compatibility path.
7. Setup presents API, detected local executable, and deterministic fixture
   choices with truthful readiness and credential-reference-only persistence.
8. `gigai create tailor-resume-for-job` opens the HTMX flow after normal setup
   without request/reference/open/model implementation flags.
9. The installed candidate passes contract, integration, installed-E2E, and
   behavioral-eval evidence required by the three spikes.
10. A v0.1.5 release candidate and sanitized handoff are ready for G24; no
    human UAT claim is made before G24 executes.

## Verification and evidence

Evidence belongs under `docs/development/evidence/phase-5/G28/` and includes
the three accepted spike decision records, role/schema vectors, tiered test reports,
behavioral eval manifests and reports, setup/create transcripts sanitized of
secrets, installed-wheel replay, and a v0.1.5 release-candidate handoff.

## Stop boundary

Stop G28 if the eval framework cannot score behavior, roles remain unbounded at
new authority boundaries, setup cannot produce a truthful usable-model choice,
or the target create command still requires implementation-facing flags.
Stop before G24 if the installed candidate does not pass all three spike
contracts and its required evidence.
