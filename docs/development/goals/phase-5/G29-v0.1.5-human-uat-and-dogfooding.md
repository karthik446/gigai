# G29 — v0.1.5 Human UAT and Dogfooding

- Status: Proposed for review; not activated
- Type: Human-executed product acceptance and dogfooding goal
- Depends on: G27 adaptive discovery, G28 v0.1.5 readiness, and the accepted
  G26/G27 runtime evidence
- Informed by: G24 exploratory 0.1.4 UAT findings; G24 is not a completion
  prerequisite because that release did not expose the full product surface
- Unblocks: G25 alpha-readiness review

## Outcome

G29 is the real operator acceptance gate for the first usable v0.1.5 product.
It tests GigAI on the operator's machine with the released package, actual
Gig definitions, adaptive questions, model configuration, local references,
SQLite state, workpad artifacts, and representative workflows.

G24 remains a useful exploratory record of the 0.1.4 experience. G29 exists
because 0.1.4 was too narrow to answer whether the complete browser-first,
model-facilitated, adaptive Gig workflow is understandable and trustworthy.

The operator drives the sessions. A review partner inspects the resulting
interaction, durable records, authority boundaries, and failures with the
operator. Neither automated tests nor a successful approval substitutes for
human acceptance.

## Contract gate

Before the first session, record:

1. the exact v0.1.5 package version and installation source;
2. the executable path and configured model target/adapter;
3. the GigAI home, workpad, and local-only UAT evidence directories;
4. the real target and references selected for each workflow;
5. the privacy, network, credential, and capability boundaries; and
6. the stop rule for unclear prompts, unexpected writes, data leakage,
   authority confusion, or unexplained persistence.

Codex, Claude, API, and local-model names are recorded only as resolved
configuration. A detected executable or nickname is not evidence of adapter
support. External model use is opt-in and must be identified in the local
record.

## Local evidence boundary

All raw UAT material stays outside Git, for example:

```text
$HOME/.gigai/uat/g29/<session-id>/
```

The sanitized record may contain package/version identifiers, command names,
resolved target and adapter names, relative artifact paths, schema/table names,
Git commit IDs, timestamps, and operator observations.

Do not commit prompts, source documents, job postings, credentials, cookies,
raw model output, full home paths, target contents, databases, or screenshots
that contain private data.

## Human session protocol

### 1. Installation and release checkpoint

Run and record:

```bash
which gigai
gigai --version
gigai --help
```

Reinstall or upgrade v0.1.5 without deleting GigAI home state. Confirm which
executable ran, which version ran, and whether the command changed state.

### 2. Setup and model checkpoint

Run `gigai setup` and `gigai doctor`. Inspect the configured model target,
readiness, endpoint/network policy, credential references, editor, home, and
workpad locations without exposing secret values.

The operator must be able to explain what GigAI can do now, what is detected
but unsupported, what requires explicit configuration, and what remains a
proposal-only capability.

### 3. Target and reference checkpoint

Run `gigai init` against a real target. Inspect Git status and the target
binding before and after. Start a create session without domain-specific
`--request` or `--reference` flags where the browser flow can collect that
information.

Confirm that local references are optional, exact, and bounded to the selected
target. Stop for unexpected target writes, remote access, credential access, or
an unclear reference boundary.

### 4. Adaptive Gig-definition checkpoint

Create at least two materially different Gigs, including:

- `tailor-resume-for-job`, with a resume and a changing job URL as Run input;
- repository review or review-and-verify; and
- one research, document, or structured-data workflow.

For each session inspect the browser interaction and record whether the model
asked useful, typed, bounded questions rather than repeating hardcoded prompts.
Confirm the session distinguishes the reusable Gig definition, stable
references and constraints, changing Run inputs, proposed Goals and outputs,
research boundaries, and unresolved decisions.

No proposal is approved until the operator can explain what approval creates
and what it does not run, write, publish, or mutate.

### 5. Durable-state checkpoint

Inspect sanitized SQLite metadata and rows, workpad manifests, journal
handoffs, proposal artifacts, and active-version state. Verify the authority
map against actual files and commits:

```text
registry.sqlite       -> target/workpad locator authority
state.sqlite          -> workpad storage container and trace
projection            -> rebuildable read projection
interview_events      -> ordered interview trace metadata
gig-proposal          -> proposal identity and approval authority
active-gig-version    -> approved version authority
journal handoff       -> lifecycle transition evidence
discovery manifest    -> subordinate discovery evidence
```

Rebuild or reopen projections only under the local UAT procedure. Confirm that
`interview_events` survives and that no projection becomes a second authority.

### 6. Revision, rejection, and approval checkpoint

Run at least one revision and one rejection. Run one explicit approval only
after the operator understands the review surface. Inspect that approval
creates/seals the expected Gig version exactly once and does not start a Run or
modify the target repository.

### 7. Improve and portability checkpoint

Where an approved Gig and bounded Run evidence are available, exercise the
improve path. Confirm original definition and references remain visible,
selected evidence is bounded and cited, and G20's evidence and quality gates
remain in the path.

Reinstall or reopen without deleting GigAI home state. Confirm prior proposals,
journal history, and approved version state remain available.

## Acceptance criteria

G29 is complete only when:

1. v0.1.5 installation, setup, model selection, and doctor output are
   understood by the operator;
2. at least two materially different Gig-definition sessions complete through
   adaptive questions and review, including `tailor-resume-for-job`;
3. local references remain optional, exact, and bounded;
4. the stable Gig definition and changing Run inputs are visibly distinct;
5. research and capability boundaries are understandable and no model output
   grants authority;
6. one revision, one rejection, and one approval are inspected;
7. SQLite, workpad, journal, proposal, discovery, and active-version authority
   are traced against actual artifacts;
8. projection rebuild/reopen preserves the interview trace and does not create
   a second authority;
9. reinstall/reopen preserves authoritative history without deleting home
   state;
10. improve evidence, where exercised, remains bounded and passes G20 gates;
11. operator and review-partner verdicts are recorded separately for every
   session; and
12. every unsafe, confusing, surprising, or unexplained result is resolved and
   re-tested or explicitly blocks G29 closeout.

## Evidence and stop boundary

Evidence remains local-only under the G29 UAT directory. The repository may
receive only a sanitized completion summary and terminal handoff after the
human sessions are complete.

Stop immediately for an unexpected target change, leaked private data,
unexplained model/network/credential use, lost history, approval ambiguity,
projection loss, or disagreement about whether the result is safe. Preserve the
local evidence and do not infer acceptance from automation.
