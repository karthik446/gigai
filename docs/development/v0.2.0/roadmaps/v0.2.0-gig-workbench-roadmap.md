# GigAI v0.2.0 — Gig workbench roadmap

**Status:** Proposed — not accepted.
This document proposes a sequencing for v0.2.0. It records operator
decisions made 2026-09-23 (D-A..D-G, below) and lays out candidate
workstreams built on the v0.1.9 spikes (S16/S17/S19/S20/S21). Nothing here
authorizes implementation, a release scope, or a Workstream 0.1.9 pull-in;
each is a proposal an operator still has to accept. No code, schema, or
test file was changed while writing this document; no live/provider call
was made. Claims are marked READ (source inspected in this worktree) or
EXECUTED (a read-only command actually run) at each citation.

## Why this document exists

The v0.2.0 discussion space (`../README.md`) asked "how do we stabilize
core into something library-like" and routed that question to S20/S21.
Separately, on 2026-09-23 the operator gave a product framing for v0.2.0
that is broader than "stable core": gigai as a personal workbench for
*many* gigs. That framing needs its own sequencing, distinct from S20's
stability-contract research — this roadmap is that sequencing. It **does
not replace** S16/S17/S19/S20/S21; see "Relationship to spikes" below.

## Operator decisions (2026-09-23, record; do not re-open)

These were given directly to the coordinator and are recorded here
verbatim-in-intent, not proposed by this document:

- **D-A — Product framing.** GigAI is a personal software workhorse to
  develop, run, and publish many gigs (roughly 10 ideas), all open source.
  Audience: the operator, plus at most ~5 people. It tracks, runs, and uses
  AIs. Optimize for "add or extend a gig easily" and "run it with one
  command" — not for third-party API stability.
- **D-B — Monorepo for now.** Gigs live in one repo until there are 4-5
  gigs with clear separation, then split. **This amends S21's decision 1**
  ("Scout moves to its own repo"), and S21 already carries the amendment,
  under its "Operator decisions (recorded, not re-opened)" section
  (`S21-gig-repos-and-data-ownership.md`, READ — cited by section heading,
  not line numbers, since S21 is still being revised in parallel by
  another worker): "Amended 2026-09-23 (D-B): monorepo for now; split into
  repos at 4-5 gigs with clear separation," amending decision 1's *timing*
  without deleting the original decision. This roadmap cites that text and
  does not edit the S21 spike.
- **D-C — One command per gig.** `gigai <gig> run` (e.g. `gigai scout run`)
  opens everything for that gig: all its goal graphs and its UI. No manual
  workpad, binding, or config ceremony.
- **D-D — Secrets.** `gigai secrets add exa` prompts for the API key and
  stores it in the gigai root folder (`~/.gigai`), where every gig can use
  it.
- **D-E — Cost visibility.** Cost is shown at the gig-dashboard level
  (search cost, etc.).
- **D-F — UI shape.** GigAI has its own UI; each gig has its own UI, added
  when the gig is running; gigai's server enforces the API rules.
- **D-G — Language and data ownership.** Python only. Gig data is
  gig-owned (S21).

```
        ├──────────────► 2 (gig-owned data, S21)

        │                      │

        └──────────────► 6 (gig authoring)          │    multi-repo

                                                      ▼    ── last
                                              (7 also needs 2 and 3)

   S (slimmer S20)  ── independent; can run anywhere, sized S
```

4, 5, and 6 depend only on 1 and run in parallel with each other and with
2→3 — they do **not** wait for 3. Workstream 7 is the one item that
depends on all of 1, 2, and 3 (see the table below), which is why it sits
last regardless of path.

| Workstream | Depends on | Notes |
| --- | --- | --- |
| 0 — Connect secrets | none | Can start immediately; smallest, most self-contained. |
| 1 — Decouple core/Scout | 0 not required | Prerequisite for 2, 3, and the "parallel after 1" group. |
| 2 — Gig-owned data | 1 | Needs the registration seam from 1 so gig data doesn't re-couple through import paths. |
| 3 — Generic runner | 1, 2 | `gigai <gig> run` needs both a gig manifest (1) and gig-owned state to point at (2). |
| 4 — Metered services | 1 | Can start once core stops assuming Scout-only clients; parallel with 5/6. |
| 5 — Hub server + UI | 1 | Needs the manifest/discovery seam to list gigs; parallel with 4/6. |
| 6 — Gig authoring | 1 | Needs the manifest shape from 1 to generate a valid new gig; parallel with 4/5. |
| 7 — Monorepo→multi-repo layout | 1, 2, 3 (a working gig contract) | Last: splitting only makes sense once there's a stable gig boundary to split along. |
| S — Slimmer S20 | none | Independent; can be picked up whenever S20's surface-freeze work is scheduled. |

### Workstream 0 — Connect secrets

**Goal:** `gigai secrets add|list|rm <service>` stores and resolves
provider API keys through gigai's existing credential-reference system,
so a gig author never has to tell an operator to `export` a key by hand.

**Size:** S.

**Dependencies:** none — can start immediately.

**Draws on:** direct code reads (below), not a numbered spike; D-D.

### Workstream 2 — Gig-owned data

**Goal:** Move Scout's records out of gigai's shared journal into Scout's
own store; split `state.sqlite` so core keeps only the G22 interview
trace; move the Scout-specific parts of `private_records`/
`application_events`/`external_recording`; gig records carry the gigai
`run_id` for cross-referencing.

**Size:** L.

**Dependencies:** Workstream 1 (needs the manifest/registration seam so
gig-owned stores don't re-couple through a new import path).

**Draws on:** S21 (`docs/development/v0.2.0/spikes/S21-gig-repos-and-data-ownership.md`,
READ, cited by section heading, not line numbers) — specifically its §2
"Data ownership migration" and its process/repo distinction in §1 "Where
the gigai/gig line falls today," whose table notes the `find-jobs`
graph/node registration currently in `bindings.py:441-450` (READ, a
source-code citation, not an S21 line citation). D-B changes *where the
gig's code lives* (monorepo for now) but not *who owns the gig's data* —
D-G restates that gig data stays gig-owned regardless of repo layout.

**Done (observably):** a fresh `gigai scout run` (once Workstream 3
exists) writes no Scout-specific records into gigai's shared
`state.sqlite`/journal tables; a focused test asserts a gig-owned store
file exists per gig and contains the gigai `run_id` linking a gig record
back to its run (path/command proposed, not yet created — S21 leaves the
exact migration approach as an open question, see "Open questions"
below).

**Pull into 0.1.9?** No. L-sized and depends on Workstream 1, which is
itself not a 0.1.9 item (see Workstream 1's reasoning above); also
directly touches the existing `state.sqlite`/journal schema, which S21
explicitly flags as an open migration question. v0.1.9's actual scope is
wave 1 (done) plus UAT fix requests on the *current* schema
(`.orchestrator/status.md` "Goal", READ) — a schema migration is the
opposite of a UAT fix, since it changes the very state UAT is currently
exercising.

**Dependencies:** Workstream 1 (manifest/discovery), Workstream 2 (a gig's

**Draws on:** S16 (registration seam), direct code reading of the current

**Done (observably):** `gigai scout run` (no subcommand, no manual

its UI from a clean checkout with secrets already set via Workstream 0;
`grep -n "find_jobs\|find-jobs" src/gigai/run.py` returns no

**Pull into 0.1.9?** No. Depends on Workstreams 1 and 2, neither of which

### Workstream 4 — Metered services

**Goal:** GigAI-owned clients for model calls and search APIs (Exa first)

**Size:** M.

**Pull into 0.1.9?** No. M-sized but depends on Workstream 1, which is not

### Workstream 5 — Hub server + UI

**Goal:** One local server; a gigai hub UI shows installed gigs, their
runs, costs, and secret status; each gig mounts its own UI + API under
`/gigs/<name>/`; loopback/consent rules are enforced by the server, not by
each gig. Scout's existing `present_api` moves under this hub.

**Size:** L.

**Dependencies:** Workstream 1 (needs gig discovery to list gigs in the
hub); runs in parallel with Workstreams 4 and 6 once 1 lands.

**Draws on:** S21 §1's note on `scout/find_jobs/present_api.py` as
Scout's own loopback API today (READ, file located at
`src/gigai/scout/find_jobs/present_api.py` in this worktree, confirmed to
exist and sized 19.1K); D-F (gigai's own UI plus per-gig UI, server
enforces API rules).

**Done (observably):** starting the hub server (`gigai serve` or
equivalent, path proposed) and visiting `http://127.0.0.1:<port>/` lists
installed gigs with run/cost/secret-status summaries; visiting
`/gigs/scout/` reaches Scout's mounted UI; a loopback-only consent check
(same shape as the existing `direct_local_ui_confirm` pattern documented
in the v0.1.8 roadmap, `v0.1.8-find-jobs-functional-roadmap.md:47`, READ)
gates any non-local network effect at the hub level, not per-gig.

**Pull into 0.1.9?** No. L-sized, depends on Workstream 1 (not a 0.1.9
item), and is a new user-facing surface — outside a version whose scope is
wave 1 (done) plus UAT fix requests on the existing single-graph Vite UI,
with only Workstream 0 flagged as a candidate pull-in.

### Workstream 6 — Gig authoring

**Goal:** `gigai new gig <name>` scaffolds a new gig from an example gig

**Size:** M.

**Dependencies:** Workstream 1 (the scaffold has to emit a manifest in
the shape Workstream 1 defines); runs in parallel with Workstreams 4 and 5
once 1 lands.

**Draws on:** S17 (`docs/development/v0.1.9/spikes/S17-gig-module-structure-classes.md`,
READ) — S17's proposed `RecordRepository`/`GigCliGroup` base classes are
what a scaffolded gig would subclass instead of copying Scout's
hand-rolled pattern a third time (S17's own framing, per its header:
"proposed core base classes so a second gig reuses a shared
implementation instead of copying Scout's pattern," `../README.md`
summary of S17, READ).

**Done (observably):** `gigai new gig demo` produces a runnable skeleton;
`gigai demo run` starts it without further edits; the same skeleton is
exercised by a core contract test, e.g. `uv run --locked --extra test
pytest tests/behaviors/gig_contract/test_example_gig.py -q` (path

## Open questions

Carried from the brief, unresolved here (this roadmap does not decide
them):

1. **Cost accounting: units vs. dollars.** Workstream 4 tracks usage units
   per gig/run/provider; whether and when that converts to a dollar figure
   for D-E's cost dashboard is open.
2. **Gig UI mounting: one app vs. many.** Workstream 5 assumes gig UIs
   mount under a single hub app (`/gigs/<name>/`); whether each gig instead
   ships a fully separate app merely *linked* from the hub is open.
3. **Existing workpad migration.** Workstream 2 moves Scout's data out of
   gigai's shared journal; whether existing operator workpads get migrated
   or operators start fresh is open.
4. **Consent/sealing/journal ceremony visibility.** How much of the
   existing consent-redemption, sealing, and journal machinery (the kind
   documented in the v0.1.8 roadmap's "Authority" row,
   `v0.1.8-find-jobs-functional-roadmap.md:48`, READ) stays visible to the
   operator versus gets hidden behind Workstream 3's defaults is open.
5. **S21's execution question.** S21 §3 "Execution ownership"
   (`S21-gig-repos-and-data-ownership.md`, READ, cited by section heading
   only, not a line number, since S21 is being revised in parallel) leaves
   open which half of *running* a graph stays in gigai versus moves to a
   gig's own process once gigs are in separate repos — not re-litigated
   here. The current lean, given D-C ("`gigai <gig> run` opens everything")
   and D-F ("gigai's server enforces the API rules"), is that gigai's
   runner keeps executing gig graphs even after a repo split; this is a
   lean, not a decision, and S21 is the authority on it.
