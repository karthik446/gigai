# GigAI v0.1.8 — Scout `find-jobs` functional roadmap

**Recorded:** 2026-09-22 · **Status:** operator-authorized implementation plan.
This is the active roadmap for one sealed Scout traversal; it makes no claim that
implementation, tests, installation, live execution, or release is complete.
Amendment 02 (Revision 3) is the contract-semantics authority; this roadmap's
DAG table below is the sole per-row ownership authority (T5).

## D10 — scope decision (2026-09-22)

> Scout is a Gig, the first of many (find product, track prices, stock
> explainer). v0.1.8's function is getting Scout out and working ASAP. More
> gigs and GigAI foundations wherever needed come in 0.2.0.

Applied here as: milestone **M1 "usable"** ahead of the installed-wheel/release
gates; a cut list for anything that does not serve M1; and a "0.2.0
generalization ledger" that records, without building, the seams gig #2 would
need.

## Goal and done-definition

| Item | Definition |
| --- | --- |
| Goal | The operator clicks **Run workflow** in the local Vite UI. One `find-jobs` traversal runs `acquire ──COMPLETE──▶ assess ──COMPLETE──▶ present`; real public postings are saved, assessed, and shown in a visible requirements × pinned-resume matrix with suggestions and questions. |
| **M1 "usable"** | From a source checkout: `yarn dev` + the local API are running; the UI shows the run scope and the operator redeems `direct_local_ui_confirm` before allocation; the operator clicks Run workflow with a real `find-jobs.json` config and their real committed resume, targeting the local model, on real public sources — M1 **is** this consented real traversal (D11/T4), not a separate step after it; they see acquisition rows and the assessment matrix. M1 needs no installed wheel and no release gate. |
| Done (post-M1) | The UI shows acquisition rows/failures and per-node status even when assessment is slow or unavailable; a successful run shows the matrix; assessment never creates tracking/application state. The graph remains fixed and linear ([P2-FREEZE-04-amendment-01-scout-graph-proof.md:57-79]; [P2-FREEZE-04-amendment-02-find-jobs-functional.md:9-17]). |
| Narrowest proof | Three separate receipts: focused source tests; M1 itself (source checkout, real config/resume, local model, consented real traversal, rows + matrix); and a clean installed wheel exercising the button/API/read path with its own separately-consented live receipt. None substitutes for the others. |

## Frozen choices and Revision 3 boundary

| Area | Plan |
| --- | --- |
| Acquire | Query-based Exa discovery with `EXA_API_KEY` from the environment and loud missing-key failure; direct ATS board clients (Greenhouse/Lever/Ashby) auto-enroll board tokens as the only new persisted record; HiringCafe sitemaps deferred (cut list). Domain filter includes `boards.greenhouse.io`, `job-boards.greenhouse.io`, `jobs.lever.co`, and `jobs.ashbyhq.com`. **Run workflow** click is the only trigger; hourly polling and backoff are non-goals (D8). Each click stores the search in an existing acquisition batch, compares normalized URL sets, filters locally against configured roles, and hashes fetched content (D1/D8; amendment:22-30). |
| Assess | Seal an explicit per-run target: `ollama_local` by default, `codex_cli` for Luna, or `openrouter_api` only after credentials exist. Missing credentials fail loudly; no silent fallback. Assess only new postings (unseen URL or edited content hash) that pass the role filter and fall within a sealed per-run cap (default 10); the rest show `not assessed` with a reason. Extends the existing proposal object with the requirements × pinned-resume matrix (`met|partial|gap`), suggestions, and questions (D2/D6; amendment:37-52). |
| Selection sealing (D6/R2) | The Run input seals `N` (cap) and the selection rule (role filter + new/edited test) before `acquire` runs. `acquire` resolves concrete candidates; the selected posting identities (URL, content hash, role match) are recorded in `AssessInput` and the assess node receipt — never in the Run input, since it is sealed before selection happens. |
| Resume and config | At run start the API resolves the newest committed `resume` private record, pins `record_id`/`revision_id`/digest into the run input (I-2 owns this resolution; D7), and shows it in the UI; no resume refuses before assess. Roles, merged queries, location/remote, publish window, source toggles, default cap, and default target live in operator-authored `<target_root>/find-jobs.json` (`workpad.py:254-297`; amendment:94-99). Config is not a persisted record; each run seals its snapshot and digest. |
| Present and consent | A top-level `ui/` Vite + React app (`yarn dev`) calls a localhost-only Python API. The button shows sources, queries, role filter, cap, and model target; confirmation sends `direct_local_ui_confirm` only through the `127.0.0.1` API, redeemed before allocation — this consent gates M1 itself, not a later step (D3/D5/D11/T4). Hosted assess additionally declares `network_read`+`credential_use` for a non-local target, covered by the same scoped UI consent. |
| Authority | Keep P3's sealed graph, additive node receipt (extended per amendment's `producer`/`usage.measured` fields), fixed binding, and the corrected aggregate status precedence `interrupted > failed > blocked > cancelled > running > pending > succeeded`. A new `graph_node_registry.py` (I-2, D11) admits real node execution for this sealed graph only: `acquire` declares `network_read`+`credential_use`+`write_workpad`; `assess` adds `network_read`+`credential_use` only for non-local, else `write_workpad`; `present` declares `write_workpad` (D4/D11; amendment "Real node execution"). |
