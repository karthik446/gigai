## The v0.1.7 pivot

GigAI's problem is that useful work performed through Codex, Claude Code, or a
similar agent is otherwise trapped in an ephemeral conversation. Research,
planning, review, and preparation should become independently reviewable,
reproducible, auditable, and reusable without making GigAI the agent's
conversation or orchestration authority.

The intended boundary is:

```text
agent is the conversational front door and configuration partner
GigAI is the local workflow, authority, evidence, review, and reuse layer
```

A Gig is a stable, high-level commission. A Run supplies the concrete task
inputs and references. The invoking agent may choose a task-sized profile,
participants, models, roles, and Goal graph. GigAI validates that draft against
the approved Gig version, records the rationale, obtains the required approval,
seals the Run Plan, and records the evidence.

The Gig must not hard-code one identical graph for every task. The task inputs,
risk, artifact type, available evidence, and user intent can change the roles
and Goal nodes selected for a Run. The agent decides what configuration is
appropriate; GigAI supplies typed vocabulary, validation, authority, evidence,
and approval.

## Runtime and consent boundary

The local companion may start with Codex or Claude Code and remain available in
the background, with a very small idle footprint. This does not authorize it to
read the whole transcript, inject hidden prompt text, make idle network calls,
scan every repository, or start a Run because an agent process exists.

Keep these concerns separate:

- background presence, IPC, health, status, and cleanup may be automatic;
- Gig creation, configuration, version approval, capability installation,
  credentials, network access, target effects, and Run execution remain
  explicit;
- the agent may recognize a repeatable workflow and propose a Gig, but the user
  approves creation and execution;
- `$gigai review`, `$gigai sync-references`, and similar commands are explicit
  entry points; model-backed operations require setup and readiness;
- `gigai doctor` reports footprint, configuration, provider, lock, and runtime
  warnings without becoming a second authority store.

Do not solve this by injecting a prompt into the user's task. Prefer runtime
hooks, native tools, structured events, or local IPC that leave the user's
conversation unchanged.

## Product surfaces to design

### Project-local packages

When the invoking agent is inside a repository, project-local Gig work belongs
under:

```text
repo/.gigai/
  gigs/
  evals/
  README.md
  .gitignore
```

`gigai init` should be explicit, idempotent, show the files and ignore rules it
will create, and never auto-commit. It must clearly distinguish the project
package from the user-local `~/.gigai` home. The generated ignore rules should
cover private/generated material such as `local/`, `runs/`, `cache/`,
`snapshots/`, `private/`, and secrets, while portable definitions and sanitized
evaluation fixtures remain check-in-able.

Portable packages must not contain credentials, absolute local paths, private
Runs, caches, installed tool bytes, or automatic install/execute hooks.

### Editing shipped Gigs

```bash
gigai clone stock-ticker-analysis
gigai create-from stock-ticker-analysis
```

`clone` creates a new identity or explicit child lineage in the project-local
package area; the source remains immutable. `create-from` uses the source as a
template, lets the agent configure the differences, generates draft JSON,
validates it, and presents a proposal. Agent-generated JSON is draft data, not
authority. User approval is required before a new Gig version exists or runs.

### Adaptive review

`review-plan` is a first-class built-in Gig, not the entire product boundary.
It should choose the smallest credible review profile for the task and expose
the selected participants, models, roles, Goal graph, tools, budgets, and
stopping rules before approval.

The VAR-shaped path is bounded and conditional:

```text
Review -> Verify -> Adjudicate -> Resolve
```

Start with cheap, short profiles. Do not make six-participant, multi-pass,
long-running plans the default; they can consume a user's account quickly.
Every profile needs explicit hard ceilings for participants, calls, passes,
loops, wall time, and usage. `deep` and `var` require explicit opt-in and must
never silently escalate or use hidden fallback.

The dashboard and Run report should make the recorded call chain inspectable:
model/role assignments, findings, evidence, disagreements, verification,
adjudication, transitions, usage, failures, and the terminal decision. This is
recorded evidence, not an attempt to expose hidden chain-of-thought.

## Candidate v0.1.7 goal sequence

These are planning names, not activated goals. Write and review each contract
before implementation:

1. **S40 — companion contract:** no prompt injection, local-only events,
   consent, lifecycle, and measurable idle footprint.
2. **G40 — tiny companion and agent adapters:** Claude/Codex integration,
   IPC/hooks, startup/shutdown, orphan recovery, and `doctor`.
3. **G41 — project-local package boundary:** repository-root detection,
   `gigai init`, selective ignore rules, and package manifests.
4. **G42 — built-in catalog:** portable `sync-references`,
   `plan-a-research`, `review-plan`, and initial standard pack.
5. **G43 — adaptive review/VAR:** task classification, bounded profiles,
   typed participants, verification, adjudication, and Run-Plan sealing.
6. **G44 — clone/create-from:** agent-configured drafts, validation,
   lineage, proposal, and approval.
7. **G45 — reference and research workflows:** repository classification,
   reference coverage, snapshots, provenance, evidence, and reports.
8. **G46 — domain Gigs:** stock analysis, job preparation, article fact-check,
   document/code/research/repository review, each with its own evaluation pack.
9. **G47 — background Runs and reports:** bounded workers, dashboard, Run
   detail, multi-model call-chain evidence, and rebuildable static exports.
10. **S48 — per-Gig quality and portability:** held-out quality, security,
    package checks, no-fallback evidence, and footprint measurements.
11. **G49 — human UAT and release decision.**
