# S45.2 — Exa-Backed Job Research Capability

**Version:** v0.1.7
**Status:** Proposed research gate — not implementation authority
**Depends on:** G46.1 Tailor v1 contract and implementation evidence, S43.3
authority-focused Adopt, and the G43.3 research-Run contract
**Unblocks:** G45.2 only if the decision is Adopt

## Question

Can GigAI use the operator's configured Exa access through the S43.3-proven
GigAI-owned broker as a bounded research capability for Codex and Claude
suggestions, while preserving direct Run consent, query privacy, provider
accounting, source provenance, and no-unattended-work boundaries?

## Research boundary

The spike is read-only research. It does not add an Exa credential, call Exa
through GigAI, implement a tool runner, or activate G45.2. It verifies Exa's
current API/terms, available search/content action shapes, attribution and
retention expectations, usage/cost accounting, response limits, result/citation
fields, and whether those controls can be represented as a sealed policy plus
sanitized replay fixtures.

The target design is deliberately narrow: a configured Exa credential reference
in machine configuration; only actions constructed by the adopted G43.3 broker;
a direct-confirmed foreground Run; and Codex/Claude suggestions validated
against a sealed public brief and budget. It rejects direct arbitrary URL
fetches, browser sessions, JavaScript, login, cookies, generic web search
outside Exa, model-supplied network endpoints, and claims of complete
job-market coverage. A model URL, citation, or tool-result claim is never an
Exa target or evidence until GigAI independently reacquires it through an
allowed action. It does not pre-decide an Exa endpoint, action name, action
limit, result-ID meaning, response size, retry rule, or cost rule; an Adopt
decision must establish those facts from provider evidence.

## Required decision record

The evidence record must choose exactly one outcome:

- **Adopt:** name the Exa API/capability version, credential-reference
  configuration boundary, broker-compatible permitted action types, canonical
  credential-free request-envelope shape, query-field mapping, per-Run
  ceilings, pre-call reservation and post-call reconciliation rules,
  response-byte measurement, result-ID lineage, retry/idempotency semantics,
  usage/cost derivation, citation/snapshot/retention fields, fixture/replay
  plan, and provider-failure behavior;
- **Narrow:** identify the missing condition and a smaller mediated Exa action
  set that could be reconsidered; or
- **Reject:** state why Exa cannot satisfy the required privacy, accounting,
  provenance, or bounded-execution contract and leave G45.2 inactive.

It may not use a model's ability to browse as evidence that GigAI can grant a
generic browsing capability. The decision must show that the outbound Exa
request excludes résumé text, private work history, credentials, cookies, and
surrounding conversation by construction.

## Acceptance and stop conditions

Adopt requires an exact policy expressible as
`urn:gigai:schema:exa-research-policy:1`, digest-pinned through an artifact
reference, with a bounded action set, role-level and Run-level limits,
machine-local credential reference, usage/cost reservation/reconciliation,
source/citation provenance, privacy-safe exact request capture, and deterministic
sanitized fixture/replay material. It must also show that both reviewed adapter
participants can make only non-authoritative suggestions, and that GigAI alone
can construct a broker action/evidence chain from them.

Stop with Narrow or Reject if Exa cannot use a configured non-secret reference,
cannot return usable citation/provenance data, cannot retain the required
private request/response artifacts under its terms, lacks bounded/recordable
usage/cost, requires unsanctioned browser or login behavior, cannot be
remain authority-mediated for both adapters, or cannot be replayed from
sanitized fixtures. No implementation may proceed on an unresolved capability.
