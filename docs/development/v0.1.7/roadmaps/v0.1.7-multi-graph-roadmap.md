## Release decision

v0.1.7 remains a CLI-first, local, durable GigAI release. Its refined product
proof is that a single approved Gig can own several independently selectable
capabilities without treating those capabilities as an implicit agent swarm or
one enormous conditional DAG.

```text
Gig version
  -> immutable Graph Set
       -> selected Goal Graph
            -> independently sealed Run Plan
                 -> one Run and its private evidence
```

A Gig is the stable product/domain boundary. It owns the shared privacy and
effect ceiling, reusable-reference namespace, evidence namespace, approval
lineage, and evaluation vocabulary. A Goal Graph is one named capability inside
that Gig. It owns its own declared inputs, outputs, references it may consume,
effects, capabilities, review policy, budget, evaluation, and evidence
requirements.

For v0.1.7, each Run selects exactly one Goal Graph. A later release may add an
approved *journey* that composes graph Runs, but it must have explicit,
digest-pinned inter-graph input/output contracts and its own consent boundary.
No Run may silently treat an earlier Run's output as input.

This does not change the established authority model:

- configuration remains machine-configuration authority;
- the registry remains project/workpad binding authority;
- proposal material is non-authoritative until explicit approval;
- journal and workpad remain lifecycle and active-version authority;
- packages remain portable definitions, never private data or runtime state;
- sealed Run Plans and Runs remain execution authority; and
- discovery, probes, candidate routing, reports, and model output remain
  evidence or projections, never approval or consent authority.

## What v0.1.7 must prove

The release must prove one private `job-search-lifecycle` Gig across two
approved versions:

```text
Job Search Lifecycle Gig v1
  -> tailor-application graph

Job Search Lifecycle Gig v2
  -> tailor-application graph (compatible carried graph)
  -> find-jobs-for-requirements graph (new graph)
```

The UAT proves that an operator can select either graph naturally or explicitly,
see why it was selected, inspect its own inputs/effects/budget, approve the v2
graph-addition revision, run either graph independently, and replay a v1 Run
against its original version. It also proves the only allowed inter-graph
handoff: a Find Run produces immutable private candidate snapshots; G46.2 may
promote one to a selectable `LEAD_ID`; and an idempotent input binding becomes
the sealed job-description input of a later Tailor Plan. The binding does not
start tailoring or grant provider consent. No graph receives another graph's
Run artifacts as ambient input.

After a closed-agent-runtime gate and additive research-Run authority are
complete, the release may support one reviewed, configured Exa research
capability. A direct-confirmed Find Run then lets Codex research and Claude
independently verify bounded Exa evidence; it does not make the operator browse
job sites manually. It does **not** need arbitrary job-board crawling,
login/cookies, browser automation, application submission, stock-data
execution, investment recommendations, graph composition, background
scheduling, application-pipeline automation, or a generic web authority
surface. Those are future domain graphs or journeys, not reasons to make the
first multi-graph proof vague.

## Core multi-graph invariants

1. An approved Gig version seals exactly one immutable Graph Set. Its digest is
   part of approval and portable-definition identity.
2. A Graph Set contains one or more content-addressed Goal Graph references.
   Every graph has a unique stable `graph_id`; aliases and routing summaries may
   not collide within the set.
3. `graph_id` is a stable semantic selector, not a new version authority.
   Changing, adding, or removing a graph creates a new Gig version and new
   Graph Set digest. v0.1.7 does not create independent graph-version counters
   or active graph pointers.
4. A Run Plan records the Graph Set reference, `selected_graph_id`, the exact
   selected Goal Graph reference, and selection provenance. These values must
   agree. A Run manifest preserves the same selected-graph evidence.
5. Shared Gig policy constrains graphs; it never grants them permission. A
   graph must explicitly declare the references, inputs, effects, capabilities,
   providers, outputs, budget, review contract, and evaluation contract it
   needs. A graph can narrow the Gig ceiling but cannot widen it.
6. A Run consumes only artifacts selected for that graph and sealed by that
   plan. Earlier Runs, other graph outputs, surrounding repositories, agent
   transcripts, and private material are not implicit input.
7. A selected graph has one defined selection source: explicit operator choice,
   a sealed G44 routing result, or the single member of a one-graph Graph Set.
   A multi-graph Run Plan with no such source fails as
   `graph_selection_required`; it never re-routes, classifies intent, or
   guesses.
8. Existing v1 proposal, approved-version, Run Plan, Run, and journal records
   remain byte-for-byte historical. A compatibility reader may project a v1
   record as a virtual one-entry Graph Set; it must not rewrite history or make
   a virtual projection a new authority record.

## Graph selection authority

G44 owns intent routing. G43.2 owns validation and sealing of an already made
selection; it must not become a second heuristic router.

G43.2 defines and validates the generic
`urn:gigai:schema:graph-selection-record:1` artifact. It is the only selection
record accepted by a multi-graph Run Plan. Its strict fields are
`schema_version`, `selection_record_id`, `gig_id`, `gig_version`, `graph_set`,
`selected_graph_id`, `selected_graph`, `selection_kind`, `selector`,
`selection_reason`, `routing_evidence_refs`, and `created_at`. `selection_kind` is exactly
`operator_explicit`, `g44_routed`, or `only_member_default`. Its conditional
schema defines `graph_set` and `selected_graph` as artifact references and
`selector` as exactly `kind`, `actor`, `rule_id`, and `rule_version`. `kind` is
exactly `operator`, `g44_router`, or `gigai_deterministic`; `actor` is an actor
or null; and `rule_id`/`rule_version` are strings or null.
`routing_evidence_refs` is an array of common artifact references. It is empty
for `operator_explicit` and `only_member_default`; it has at least one
safe-to-display artifact reference for `g44_routed`. `operator_explicit`
requires an operator actor and null rule fields; `g44_routed` requires a
`g44_router` selector with non-null G44 rule ID/version and routing evidence;
and `only_member_default` requires a GigAI-owned deterministic selector with
null rule fields and no routing evidence. No other source is valid.

The only permitted selection sources are therefore:

1. an explicit operator graph selection;
2. a G44-produced `g44_routed` graph-selection record selected as an exact
   sealed Plan input; or
3. an `only_member_default` when the approved Graph Set contains exactly one
   graph.

With a multi-graph Graph Set, absent or invalid selection is
`graph_selection_required`, even if a different component could make a
plausible inference. The Plan records the selection kind, actor identity or
routing evidence, Graph Set digest, `graph_id`, and exact Goal Graph reference.
Its validator rejects any disagreement among those values. G44 later becomes a
producer of the already-defined `g44_routed` record; it does not own or revise
this schema. A selection record is evidence, not Run authority; direct Run
consent and the sealed Plan remain required.

## Graph Descriptor, compatibility, and schema boundary

G43.2 must be additive. It introduces a strict, content-addressed Graph Set
artifact and versioned readers/writers for the multi-graph authority chain. Its
contract must state the exact schema IDs, storage paths, required fields,
semantic validation, canonical digest procedure, and migration/read rules
before implementation.

Every Graph Set entry is a strict generic Graph Descriptor, not merely a list
of Goal Graph references. It must bind, through exact artifact references or
typed fields:

- stable `graph_id`, purpose, aliases, and safe routing summary;
- the one Goal Graph reference;
- graph-local input, output, and reference-consumption contracts;
- effect policy and capability requirements;
- provider/model eligibility policy, without concrete machine-local targets,
  credentials, or discovery evidence;
- graph budget ceiling;
- review contract, evaluation contract, and completion-evidence contract.

The G43.2 semantic validator must prove that the entire descriptor agrees with
the enclosing Graph Set and narrows rather than widens the approved shared Gig
policy. It rejects a selected graph whose attached contracts, effect set,
capability requirements, provider eligibility, or budget conflict with that
set or its shared ceiling.

The minimum chain to reconcile is:

```text
proposal
  -> approved active Gig version
       -> Graph Set + selected Goal Graph
            -> sealed Run Plan
                 -> Run handoff / Run manifest / Run details
                      -> comparison, portability, report projections
```

The proposal, active-version record, Run Plan, and Run manifest must not permit
a mix-and-match Graph Set digest, graph ID, and graph reference. Every
projection that presently reports one `goal_graph` must either report the
selected graph plus its Graph Set or state that it is reading a legacy v1
record. Catalog/package evolution remains portable-definition work only; it
creates no new installation record or private-data authority.

### G43.2 — Multi-Graph Gig Versions and graph-selected Run Plans

**Depends on:** G43 and the completed G43.1 closeout
**Owns:** the Graph Set artifact, multi-graph Gig-version authority, selected
graph sealing, v1 compatibility readers, and structural fixtures.

**Acceptance evidence:**

- Graph Set schema/semantic rejection for duplicate IDs, aliases, malformed
  references, and mismatched digests;
- Graph Descriptor validation for every required graph-local contract,
  including provider/model eligibility policy without machine-local targets or
  credentials;
- mutation tests proving a graph cannot widen the shared Gig effect,
  capability, provider-eligibility, or budget ceiling, and proving that every
  selected graph contract agrees with its Graph Set;
- v2 approval binds a whole Graph Set while a new/changed graph creates a new
  Gig version;
- a Run Plan seals one valid selected graph only from explicit operator
  selection, a sealed G44-produced graph-selection record, or a one-member
  default; it returns `graph_selection_required` for every other multi-graph
  case;
- schema and semantic tests reject every invalid graph-selection record,
  including a mismatched Gig/version/Graph Set/graph reference, an unsupported
  selection kind, and a G44-routed record without its required routing evidence;
- Run handoff and manifest preserve matching Graph Set and selected-graph
  evidence;
- v1 historical approval and Run records remain unchanged and can be read as
  a virtual one-entry set only; and
- deterministic, domain-neutral Job Search Lifecycle and Stock Graph Set
  fixtures validate structure without claiming their workflows execute.

G43.2 may carry a graph's declared research-effect ceiling as structural policy
data, but it does not create research phases, participant roles, broker
authority, non-zero tool budgets, or a new Run Plan schema. G45.2 depends on
the separate G43.3 authority increment for those concerns.

### S43.3 — Authority-focused agent mediation feasibility

**Depends on:** G40, completed G43.1, and completed G43.2
**Unblocks:** G43.3 only on Adopt
**Status:** Proposed amended gate — historical closed-runtime inquiry is Reject;
the [authority-focused amendment](../../evidence/v0.1.7/S43.3/authority-focused-amendment.md)
requires a fresh decision.

S43.3 proves whether Codex and Claude can act as untrusted public-research
participants while GigAI alone constructs authoritative IDs, broker requests,
evidence, lineage, reservations, and consent. A participant's direct URL,
citation, claim, or tool result remains a suggestion until GigAI reacquires and
validates it. The gate proves GigAI-observed invocation/broker accounting, not
unobservable internal CLI turns or native tools. It additionally requires
disclosure-isolated launches: a fresh execution root, fresh empty `HOME`,
`CODEX_HOME`, XDG, and `TMPDIR` paths, a fixed allowlist and resolved
executable, with no inherited home/worktree instructions, memories, caches,
credentials, or configuration. Deterministic fixtures prove that GigAI wrapper
only; Adopt additionally requires one bounded public marker invocation through
each exact configured Codex and Claude adapter using a separately proven
isolated authentication channel. The resulting digest-bound, expiring
authentication-channel proofs are reusable target/adapter/channel evidence;
each later research Plan separately binds its participant to a proof and
revalidates the current non-secret configuration digest. Marker probes are
direct-confirmed, explicitly reserved provider calls, never Plan-construction
or consent-preview side effects; their versioned records contain the exact
safe accounting/identity evidence used by the proof. Every participant
invocation revalidates proof expiry, executable digest, and configuration
digest immediately before prompt assembly.
Private and local-only inputs stay outside unrestricted participant context;
Tailor requires a restricted adapter path. A later verifier may receive only a
GigAI-generated public evidence view containing exact broker lineage,
sanitized approved public fields, and opaque result handles—never raw provider
bytes, URLs, citations, or result identifiers.

### G43.3 — Brokered agent research Run authority

**Depends on:** completed G43, completed G43.2, and S43.3 authority-focused Adopt
**Status:** Pending S43.3 authority-focused Adopt and completed G43.1/G43.2.
**Owns:** additive `run-plan:2`, `research-standard@1`, research roles/phases,
participant math, authenticated broker lifecycle, reservations/reconciliation,
and generic broker event evidence.

G43.3 preserves every `run-plan:1` and existing G43 profile byte/meaning. Its
new research profile is the only authority that can turn a public participant
suggestion into a bounded broker action. It also owns the generic
broker-generated public evidence view and opaque result-handle protocol. It is
provider/domain-neutral: it does not define Exa payloads, lead policy, job
relevance, or lead selection. `run-plan:2` seals a human-readable runtime
disclosure; the direct `--confirm` preview states that participants are
unrestricted public-suggestion sources and GigAI accounts only for its own
invocations and broker events, not unobservable native CLI activity.

### G44 — Graph-aware intent routing and Gig/graph candidates

**Depends on:** G43.2
**Contract work may proceed in parallel with:** G45

G44 retains its existing useful distinction among `existing_gig`, `one_off`,
`gig_candidate`, `revision_candidate`, and `needs_operator_input`. It is
amended to emit a typed routing record for one selected `graph_id`, with its
selection reason and only its missing inputs. It produces the
`g44_routed` graph-selection record already defined by G43.2; G43.2 later
validates and seals that record as a selected Plan input, but does not re-route
it. Explicit Gig/graph selection always wins over heuristic routing.

A request to extend a named Gig creates a private revision candidate that says
whether it proposes `add_graph`, `modify_graph`, `remove_graph`, or
`change_shared_policy`. It cannot alter the active Gig, add a graph silently,
or convert a prior Run into input. Candidate material stays private,
non-executable, and non-authoritative until the normal proposal, review, and
approval lifecycle creates a new Gig version.

### G45 — Private references and explicit Run inputs

**Depends on:** G43.2 for graph-specific binding
**Contract work may proceed in parallel with:** G44

G45 remains shared local private-evidence infrastructure, not a general
crawler. It supports explicit local text references and pasted/local Run inputs
for Tailor v1. G45.2 follows S43.3 authority-focused Adopt, completed G43.3,
and an S45.2 Adopt decision and owns bounded
Exa-backed agent research, citation/lead snapshots, and explicit
lead-to-job-description input binding. Graph contracts state which reference
and input kinds they may consume; the sealed Run Plan binds only those selected
for its selected graph. Private material never enters a portable package,
catalog fixture, committed evidence, or another graph's Run by implication.

### G46 — Domain Gig families and evaluation packs

**Depends on:** G43.2, G44, and G45

G46 defines the private Job Search Lifecycle Gig family: its v0.1.7 commission
is operator-started agent research and application tailoring only. It
distinguishes shared Gig governance from graph-specific contracts, defines
graph naming and discovery, shared-policy narrowing, graph-addition/removal
compatibility, per-graph evaluation ownership, and the explicit lead-to-input
handoff. Its Find graph additionally depends on G43.3 and G45.2; quality
evidence from one graph must never prove another graph's quality.

### G46.1 — Job Search Lifecycle Gig v1: `tailor-application`

**Depends on:** G43.2, G45, and G46
**Delivery:** private foreground dogfood; not a G42 catalog entry

The existing `tailor-resume-for-job` contract becomes the first graph in a
private `job-search-lifecycle` Gig. It retains its present bounded behavior:
explicit private résumé/project references, pasted job description, truthful
tailored artifacts, no-invention evidence, untouched originals, standard@1
review, and no job finding, URL fetching, application submission, or external
mutation. It additionally requires a separately proven restricted adapter
before private material enters any provider prompt; the public-research
participant exception never applies to Tailor.

### S45.2 — Exa-backed job research capability gate

**Depends on:** G46.1, S43.3 authority-focused Adopt, and the G43.3 contract

S45.2 decides whether Exa can be used through the GigAI-owned broker boundary
with accounted, bounded actions and retainable citation evidence. Its Adopt
output, not downstream target prose or agent claims, freezes the Exa
policy/action shapes/limits/cost derivation. It must Adopt, Narrow, or Reject

### G45.2 — Bounded Exa research and lead bindings

**Depends on:** S43.3 authority-focused Adopt, completed G43.3, S45.2 Adopt, G45, and G43.2

G45.2 owns the Exa-specific sealed policy, canonical private request/response
evidence, provider accounting derivation, citation/lead structural records,
and operator-confirmed idempotent lead-to-job-description binding. G43.3 owns

terminal-result policy. G45.2 has no schedule, browser, credential,

### G46.2 — Job Search Lifecycle Gig v2: `find-jobs-for-requirements`

**Depends on:** G43.3, G44, G45.2, G46, and G46.1

G46.2 proves an explicitly operator-approved v2 of the same Job Search
Lifecycle Gig adding the independently selectable
`find-jobs-for-requirements` graph. A direct-confirmed foreground Run assigns
Codex primary research and Claude independent research/verification under the
selected G45.2 Exa policy. It owns the rules that promote structural candidate
evidence to a surfaced/selectable job lead and the Find terminal-result algebra.
It produces immutable private citation/candidate snapshots,
requirement-grounded relevance reasons, and rebuildable report artifacts; an
operator must select a promoted lead explicitly before Tailor can use it.

Its acceptance includes success, no matching jobs, stale results, malformed
content, duplicate leads, Exa/provider failure, role/Run budget exhaustion,
cancellation, independent graph invocation, and historical v1 replay.

### G47 — Foreground graph-aware reporting

**Depends on:** G43.2, G43.3, G45, G45.2, G46, G46.1, and G46.2

G47 adds rebuildable, read-only foreground CLI/JSON/Markdown/optional-static

### v0.1.8 carry-forward

v0.1.8 may add graph-specific schedules and an append-only private application
pipeline. System evidence may record `discovered`; only the operator may append

may consult a rebuildable current-state projection for suppression/deduplication

submission remain off by default.

### S48 and G49 — Release evidence and human UAT

S48 evaluates Graph correctness, Graph Set integrity/compatibility,
Exa/citation provenance/privacy, and Gig-level routing/discoverability
independently. G49 performs the terminal human UAT through setup, intent

## Release-wide stop conditions

Stop and record a failed or blocked gate if any of these occurs:

- a Graph Set, graph selection, or compatibility projection can select a graph
  without the approved Gig version;
- a graph change becomes active without a new approved Gig version;
- a shared policy is treated as a capability grant, or a graph silently widens
  it;
- a graph reads another graph's Run output, a prior Run, ambient files, or an
  agent transcript without an explicit sealed artifact reference;
- a route guesses between plausible graphs when that choice changes data,
  privacy, effects, or authority;
- legacy v1 records are rewritten or become invalid merely because v2 exists;
- provider review uses unselected inputs, target effects, hidden fallback,
  unbounded budgets, or missing direct consent;
- job research runs before S43.3 and G43.3 complete, invokes Exa outside its
  GigAI-owned sealed policy/budget, calls it before direct Run consent, permits
  a participant-supplied URL/citation/result to become an action or evidence,
  or sends résumé text/private history/local-only requirements to an
  unrestricted participant;
- a lead is turned into a Tailor input without direct operator confirmation, a
  digest-bound binding, separate Plan sealing, and separate direct Run consent;
- a foreground report refreshes a source, invokes a provider, modifies evidence,
  or implies scheduled/application-pipeline behavior; or
- private references, Run evidence, credentials, absolute paths, or runtime
  state enter portable packages, catalog fixtures, or committed evidence; or
- reporting cannot rebuild the Gig, Graph Set, selected graph, Run, and
  evidence relationship from authoritative local artifacts.

## Addendum — 2026-09-07: shipped Job Search Lifecycle and agent teams

The operator's refined v0.1.7 outcome is a shipped, reusable
`job-search-lifecycle` template that any user can initialize and personalize
through Codex or Claude. Users should not need to author a Gig with `create`
to use the included workflow. Proposed `gigai init job-search-lifecycle` and
its `jsl` alias establish or reopen the user's private instance; bare `init`
retains its workspace meaning. These commands are proposed, not implemented.

The release includes role research, progressive preferences and experience
capture, job discovery, resume/cover-letter tailoring with inspectable checks,
user-recorded application progress, and interview preparation. Selected
artifacts and answers persist across graphs and sessions, with exact input
snapshots retained for each Run. Workflow changes create Gig versions;
ordinary preference or job-input changes do not require workflow redesign.

For this iteration, the user's external agent performs research and other
semantic work using its own authorized capabilities. GigAI supplies the
workflow definition, explicit input/output boundary, durable records,
validation, inspection, and review integration. Agent-supplied research is
recorded with provenance and verification status; storage does not establish
factual correctness or claim that GigAI observed the agent's internal activity.

This changes the preceding release plan in these specific ways:

- The private-only G46 dogfood becomes a shipped template plus private user
  instances; G41/G42 installation and G44 routing require explicit amendments.
- Role research and interview preparation become release capabilities.
- Manual application-state recording moves into v0.1.7. Scheduling,
  submission, outreach, and automatic application-state inference remain
  outside this release.
- S43.3/G43.3/S45.2/G45.2's GigAI-owned Exa broker is deferred from this
  release path. Its historical Reject and proposed amendments remain intact;
  this decision does not claim those gates passed or authorize that broker.
- The external-agent execution/recording contract must be defined explicitly.
  It must not masquerade as the restricted adapter promised by the prior
  private Tailor contract or manufacture direct-operator consent.
- Supporting code, explicit conversation records, instance customization,
  and portability receive bounded contracts in the replacement roadmap.
- Implementation teams may work in parallel once their dependency contracts
  and file ownership are settled. The old restriction to parallel contract
  work is replaced by the new roadmap's dependency and integration rules.

The [replacement roadmap](v0.1.7-scout-roadmap.md) defines the
SCOUT-00 through SCOUT-12 delivery goals, acceptance evidence, team ownership, and
release gate. These are development work items, not runtime Goal Graph IDs.
G40-G43 foundations and the pending G43.1 closeout are reused. Existing
approval lineage, private-data separation, historical Run readability, and
honest evidence/accounting remain requirements.

This addendum records the requested planning change only. No implementation,
provider Run, goal activation, release publication, or claim of completed
Job Search Lifecycle behavior is created by this document.
