# GigAI v0.1.7 Multi-Graph Roadmap

**Date:** 2026-09-03
**Status:** Proposed — current v0.1.7 planning authority; individual Goal
contracts still require review and activation before implementation
**Supersedes:** [`v0.1.7-roadmap.md`](v0.1.7-roadmap.md)
**Baseline:** v0.1.6 / `main` at `7f9ceb5`

## Release decision

v0.1.7 remains a CLI-first, local, durable GigAI release. Its refined product
proof is that a single approved Gig can own several independently selectable
capabilities without treating those capabilities as an implicit agent swarm or
one enormous conditional DAG.

```text
Gig version
  -> immutable Graph Set
       -> selected Goal Graph
            -> independently sealed Run Plan
                 -> one Run and its private evidence
```

A Gig is the stable product/domain boundary. It owns the shared privacy and
effect ceiling, reusable-reference namespace, evidence namespace, approval
lineage, and evaluation vocabulary. A Goal Graph is one named capability inside
that Gig. It owns its own declared inputs, outputs, references it may consume,
effects, capabilities, review policy, budget, evaluation, and evidence
requirements.

For v0.1.7, each Run selects exactly one Goal Graph. A later release may add an
approved *journey* that composes graph Runs, but it must have explicit,
digest-pinned inter-graph input/output contracts and its own consent boundary.
No Run may silently treat an earlier Run's output as input.

This does not change the established authority model:

- configuration remains machine-configuration authority;
- the registry remains project/workpad binding authority;
- proposal material is non-authoritative until explicit approval;
- journal and workpad remain lifecycle and active-version authority;
- packages remain portable definitions, never private data or runtime state;
- sealed Run Plans and Runs remain execution authority; and
- discovery, probes, candidate routing, reports, and model output remain
  evidence or projections, never approval or consent authority.

## What v0.1.7 must prove

The release must prove one private `career-preparation` Gig across two approved
versions:

```text
Career Gig v1
  -> tailor-application graph

Career Gig v2
  -> tailor-application graph (compatible carried graph)
  -> interview-prep graph (new graph)
```

The UAT proves that an operator can select either graph naturally or explicitly,
see why it was selected, inspect its own inputs/effects/budget, approve the v2
graph-addition revision, run either graph independently, and replay a v1 Run
against its original version. The graphs may share explicitly selected private
references; neither receives the other graph's Run artifacts as ambient input.

The release does **not** need job-board crawling, application submission,
stock-data execution, investment recommendations, graph composition,
background scheduling policy, browser automation, or a second web authority
surface. Those are future domain graphs or journeys, not reasons to make the
first multi-graph proof vague.

## Core multi-graph invariants

1. An approved Gig version seals exactly one immutable Graph Set. Its digest is
   part of approval and portable-definition identity.
2. A Graph Set contains one or more content-addressed Goal Graph references.
   Every graph has a unique stable `graph_id`; aliases and routing summaries may
   not collide within the set.
3. `graph_id` is a stable semantic selector, not a new version authority.
   Changing, adding, or removing a graph creates a new Gig version and new
   Graph Set digest. v0.1.7 does not create independent graph-version counters
   or active graph pointers.
4. A Run Plan records the Graph Set reference, `selected_graph_id`, the exact
   selected Goal Graph reference, and selection provenance. These values must
   agree. A Run manifest preserves the same selected-graph evidence.
5. Shared Gig policy constrains graphs; it never grants them permission. A
   graph must explicitly declare the references, inputs, effects, capabilities,
   providers, outputs, budget, review contract, and evaluation contract it
   needs. A graph can narrow the Gig ceiling but cannot widen it.
6. A Run consumes only artifacts selected for that graph and sealed by that
   plan. Earlier Runs, other graph outputs, surrounding repositories, agent
   transcripts, and private material are not implicit input.
7. A selected graph has one defined selection source: explicit operator choice,
   a sealed G44 routing result, or the single member of a one-graph Graph Set.
   A multi-graph Run Plan with no such source fails as
   `graph_selection_required`; it never re-routes, classifies intent, or
   guesses.
8. Existing v1 proposal, approved-version, Run Plan, Run, and journal records
   remain byte-for-byte historical. A compatibility reader may project a v1
   record as a virtual one-entry Graph Set; it must not rewrite history or make
   a virtual projection a new authority record.

## Graph selection authority

G44 owns intent routing. G43.2 owns validation and sealing of an already made
selection; it must not become a second heuristic router.

G43.2 defines and validates the generic
`urn:gigai:schema:graph-selection-record:1` artifact. It is the only selection
record accepted by a multi-graph Run Plan. Its strict fields are
`schema_version`, `selection_record_id`, `gig_id`, `gig_version`, `graph_set`,
`selected_graph_id`, `selected_graph`, `selection_kind`, `selector`,
`selection_reason`, `routing_evidence_refs`, and `created_at`. `selection_kind` is exactly
`operator_explicit`, `g44_routed`, or `only_member_default`. Its conditional
schema defines `graph_set` and `selected_graph` as artifact references and
`selector` as exactly `kind`, `actor`, `rule_id`, and `rule_version`. `kind` is
exactly `operator`, `g44_router`, or `gigai_deterministic`; `actor` is an actor
or null; and `rule_id`/`rule_version` are strings or null.
`routing_evidence_refs` is an array of common artifact references. It is empty
for `operator_explicit` and `only_member_default`; it has at least one
safe-to-display artifact reference for `g44_routed`. `operator_explicit`
requires an operator actor and null rule fields; `g44_routed` requires a
`g44_router` selector with non-null G44 rule ID/version and routing evidence;
and `only_member_default` requires a GigAI-owned deterministic selector with
null rule fields and no routing evidence. No other source is valid.

The only permitted selection sources are therefore:

1. an explicit operator graph selection;
2. a G44-produced `g44_routed` graph-selection record selected as an exact
   sealed Plan input; or
3. an `only_member_default` when the approved Graph Set contains exactly one
   graph.

With a multi-graph Graph Set, absent or invalid selection is
`graph_selection_required`, even if a different component could make a
plausible inference. The Plan records the selection kind, actor identity or
routing evidence, Graph Set digest, `graph_id`, and exact Goal Graph reference.
Its validator rejects any disagreement among those values. G44 later becomes a
producer of the already-defined `g44_routed` record; it does not own or revise
this schema. A selection record is evidence, not Run authority; direct Run
consent and the sealed Plan remain required.

## Graph Descriptor, compatibility, and schema boundary

G43.2 must be additive. It introduces a strict, content-addressed Graph Set
artifact and versioned readers/writers for the multi-graph authority chain. Its
contract must state the exact schema IDs, storage paths, required fields,
semantic validation, canonical digest procedure, and migration/read rules
before implementation.

Every Graph Set entry is a strict generic Graph Descriptor, not merely a list
of Goal Graph references. It must bind, through exact artifact references or
typed fields:

- stable `graph_id`, purpose, aliases, and safe routing summary;
- the one Goal Graph reference;
- graph-local input, output, and reference-consumption contracts;
- effect policy and capability requirements;
- provider/model eligibility policy, without concrete machine-local targets,
  credentials, or discovery evidence;
- graph budget ceiling;
- review contract, evaluation contract, and completion-evidence contract.

The G43.2 semantic validator must prove that the entire descriptor agrees with
the enclosing Graph Set and narrows rather than widens the approved shared Gig
policy. It rejects a selected graph whose attached contracts, effect set,
capability requirements, provider eligibility, or budget conflict with that
set or its shared ceiling.

The minimum chain to reconcile is:

```text
proposal
  -> approved active Gig version
       -> Graph Set + selected Goal Graph
            -> sealed Run Plan
                 -> Run handoff / Run manifest / Run details
                      -> comparison, portability, report projections
```

The proposal, active-version record, Run Plan, and Run manifest must not permit
a mix-and-match Graph Set digest, graph ID, and graph reference. Every
projection that presently reports one `goal_graph` must either report the
selected graph plus its Graph Set or state that it is reading a legacy v1
record. Catalog/package evolution remains portable-definition work only; it
creates no new installation record or private-data authority.

### Current closeout

#### G43.1 — Provider-backed document-review execution

G43.1 remains active until its dogfood is honest and complete. The completed
Codex-only review is intermediate evidence, not closure. Before the final
provider dogfood, freeze an operator-approved public G44 requirements baseline
as a second, separately sealed review input. This small closure preparation is
not G44 activation, graph-aware routing work, or early G43.2 implementation.

Closure then requires a real configured Claude target and a real configured
Codex target reviewing the same public G44 contract and baseline, a
human-applied G44 correction when a valid finding exists, and a fresh
sealed-plan re-review. It must retain direct Run consent, selected-input-only
reading, bounded accounting, and no target-repository effects.

### G43.2 — Multi-Graph Gig Versions and graph-selected Run Plans

**Depends on:** G43 and the completed G43.1 closeout
**Owns:** the Graph Set artifact, multi-graph Gig-version authority, selected
graph sealing, v1 compatibility readers, and structural fixtures.

**Acceptance evidence:**

- Graph Set schema/semantic rejection for duplicate IDs, aliases, malformed
  references, and mismatched digests;
- Graph Descriptor validation for every required graph-local contract,
  including provider/model eligibility policy without machine-local targets or
  credentials;
- mutation tests proving a graph cannot widen the shared Gig effect,
  capability, provider-eligibility, or budget ceiling, and proving that every
  selected graph contract agrees with its Graph Set;
- v2 approval binds a whole Graph Set while a new/changed graph creates a new
  Gig version;
- a Run Plan seals one valid selected graph only from explicit operator
  selection, a sealed G44-produced graph-selection record, or a one-member
  default; it returns `graph_selection_required` for every other multi-graph
  case;
- schema and semantic tests reject every invalid graph-selection record,
  including a mismatched Gig/version/Graph Set/graph reference, an unsupported
  selection kind, and a G44-routed record without its required routing evidence;
- Run handoff and manifest preserve matching Graph Set and selected-graph
  evidence;
- v1 historical approval and Run records remain unchanged and can be read as
  a virtual one-entry set only; and
- deterministic, domain-neutral Career and Stock Graph Set fixtures validate
  structure without claiming their workflows execute.

### G44 — Graph-aware intent routing and Gig/graph candidates

**Depends on:** G43.2
**Contract work may proceed in parallel with:** G45

G44 retains its existing useful distinction among `existing_gig`, `one_off`,
`gig_candidate`, `revision_candidate`, and `needs_operator_input`. It is
amended to emit a typed routing record for one selected `graph_id`, with its
selection reason and only its missing inputs. It produces the
`g44_routed` graph-selection record already defined by G43.2; G43.2 later
validates and seals that record as a selected Plan input, but does not re-route
it. Explicit Gig/graph selection always wins over heuristic routing.

A request to extend a named Gig creates a private revision candidate that says
whether it proposes `add_graph`, `modify_graph`, `remove_graph`, or
`change_shared_policy`. It cannot alter the active Gig, add a graph silently,
or convert a prior Run into input. Candidate material stays private,
non-executable, and non-authoritative until the normal proposal, review, and
approval lifecycle creates a new Gig version.

### G45 — Private references and explicit Run inputs

**Depends on:** G43.2 for graph-specific binding
**Contract work may proceed in parallel with:** G44

G45 remains shared private-evidence infrastructure, not a general crawler.
The first increment supports explicit local text references and pasted/local
Run inputs for the private Career Gig. Graph contracts state which reference
and input kinds they may consume; the sealed Run Plan binds only those selected
for its selected graph. Private material never enters a portable package,
catalog fixture, committed evidence, or another graph's Run by implication.

### G46 — Domain Gig families and evaluation packs

**Depends on:** G43.2, G44, and G45

G46 defines when several graphs belong to the same Gig and distinguishes shared
Gig governance from graph-specific contracts. It defines graph naming and
discovery, shared-policy narrowing, graph-addition/removal compatibility,
per-graph evaluation ownership, and explicit output handoff rules for a later
journey. Quality evidence from one graph must never prove another graph's
quality.

### G46.1 — Career Gig v1: `tailor-application`

**Depends on:** G45 and G46
**Delivery:** private foreground dogfood; not a G42 catalog entry

The existing `tailor-resume-for-job` contract becomes the first graph in a
private `career-preparation` Gig. It retains its present bounded behavior:
explicit private résumé/project references, pasted job description, truthful
tailored artifacts, no-invention evidence, untouched originals, standard@1
review, and no job finding, URL fetching, application submission, or external
mutation.

### G46.2 — Career Gig v2: add `interview-prep`

**Depends on:** G46.1

G46.2 proves an explicitly operator-approved v2 of the same Career Gig adding
a second, independently selectable `interview-prep` graph. Its first increment
uses only explicitly supplied local/pasted sources. It may produce a
role/company briefing, likely interview themes, evidence-grounded stories,
skill-gap questions, interviewer questions, a practice rubric, and a
preparation checklist. It does not crawl company sites, access job boards,
schedule interviews, or communicate with any third party.

Its acceptance proves v1 Run replay, v2 graph-addition lineage, graph-specific
reference/input/effect enforcement, and independent invocation of either
Career graph.

### G47 — Graph-aware background Runs and reporting

**Depends on:** G43.2, G45, G46, and G46.2

Any schedule, worker, cancellation, recovery record, or report targets one
`gig_id + gig_version + graph_id`; it never means “run the whole Gig.” G47
preserves foreground/background equivalence and rebuildable CLI/JSON/Markdown
reports, organized by Gig, Graph Set, selected graph, version, and Run.

### S48 and G49 — Release evidence and human UAT

S48 evaluates Graph correctness, Graph Set integrity/compatibility, and
Gig-level routing/discoverability independently. G49 performs the terminal
human UAT through setup, intent routing, proposal, approval, graph selection,
Run Plan sealing, direct consent, execution, evidence inspection, graph
addition, and historical replay. Provider, security, privacy, portability,
recovery, and no-fallback evidence remain release gates.

## Dependency and delivery order

```text
freeze operator-approved G44 dogfood requirements baseline
  -> finish Claude + Codex G43.1 review
       -> human correction and fresh re-review
            -> close G43.1 honestly
                 -> contract and implement G43.2
                      -> contract G44 graph-aware routing   ┐
                      -> contract G45 private inputs/refs   ┘ (parallel contract work)
                           -> define G46 domain-family contract
                                -> Career Gig v1: tailor-application
                                     -> Career Gig v2: add interview-prep
                                          -> multi-graph UAT and historical replay
                                               -> G47 -> S48 -> G49
```

Parallelism is limited to independent contract work. Implementations that read
or write Graph Set authority remain ordered behind G43.2. G44, G45, or domain
work may not create a shortcut around approval, sealed plans, direct Run
consent, graph-specific inputs, or evaluation evidence.

## Release-wide stop conditions

Stop and record a failed or blocked gate if any of these occurs:

- a Graph Set, graph selection, or compatibility projection can select a graph
  without the approved Gig version;
- a graph change becomes active without a new approved Gig version;
- a shared policy is treated as a capability grant, or a graph silently widens
  it;
- a graph reads another graph's Run output, a prior Run, ambient files, or an
  agent transcript without an explicit sealed artifact reference;
- a route guesses between plausible graphs when that choice changes data,
  privacy, effects, or authority;
- legacy v1 records are rewritten or become invalid merely because v2 exists;
- provider review uses unselected inputs, target effects, hidden fallback,
  unbounded budgets, or missing direct consent;
- private references, Run evidence, credentials, absolute paths, or runtime
  state enter portable packages, catalog fixtures, or committed evidence; or
- reporting cannot rebuild the Gig, Graph Set, selected graph, Run, and
  evidence relationship from authoritative local artifacts.
