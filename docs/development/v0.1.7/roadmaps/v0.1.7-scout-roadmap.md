## Release outcome

The operator's immediate target is personal use of Scout. Broader onboarding/UI
research and research into memory-driven Gig improvement are recorded as
[v0.1.8 spikes](../../v0.1.8/spikes/README.md), to start after Scout. They do

**2026-09-09 release-scope addition:** After Scout implementation, ship

in GigAI itself. Compare Qwen + local Ollama harness with Luna + Codex on the
same Gig-owned cases. Scout is the first consumer, not the owner of backend
infrastructure. This is a new required v0.1.7 goal, not covered by historical
SCOUT-00 approval; its detailed contract needs independent review. Broader
local-model research remains v0.1.8. No current worker is redirected by this addition.

A new user installs GigAI and uses the included Scout Gig
through Codex or Claude. They can research a role, find opportunities, tailor
application material, record application progress, and prepare for interviews.
Their references, preferences, answers, research, documents, and previous work
remain available when they return with a fresh agent session.

The user does not author a workflow to begin using the shipped capability.
They may subsequently customize their private instance or create a different
Gig from scratch. Scout is the first concrete product proof of
GigAI as a system for building and improving user-specific software.

Proposed entry points, to be implemented and tested:

```text
Agent: "Use GigAI to help me pursue forward deployed engineer roles."

Explicit CLI equivalent:
gigai init
# Non-interactive form when the user has provided a username:
gigai init --username NAME --json
```

General initialization obtains an explicit username and creates the user's
private default instance of every release-eligible bundled default Gig,
including Scout, in the selected project/workspace. Non-interactive init
returns `username_required` if neither a saved nor explicit username exists.
Users do not run a clone command for each default. `init scout`, personal
suffixes, and old `jsl`/`job-search-lifecycle` aliases are not required or
introduced by this v0.1.7 contract. Scout remains the canonical template name.

This deliberately extends the earlier bare-init workspace-only design.
Username is owner display metadata, not an OS account, filesystem path,
authentication mechanism, or Gig ID. Full IDs and project/template/default
bindings preserve identity. Repeated init returns existing instances, resumes
partial provisioning, and adds newly bundled defaults without replacing user
customizations or selecting an arbitrary active Gig. A username conflict
refuses rather than recreating instances. Package installation itself does
not create workspaces. `gigai create` remains custom authoring. Initialization
shows each proposal/approval state and never executes copied tools, starts a
workflow, probes providers, or grants approval/Run consent.

## Lifecycle and progressive onboarding

The shipped template has independently selectable capabilities with the
following proposed graph IDs. SCOUT-00 freezes their final contracts.

| Graph | Inputs and questions | Durable result |
|---|---|---|
| `research-role` | Target role, research questions; geography/currency when needed for compensation context | Responsibilities, role variations, compensation findings, sources, uncertainty, further questions |
| `find-jobs` | Selected preferences and optional candidate evidence; missing material search constraints | Job snapshots, source records, fit reasons, sponsorship/compensation uncertainty, shortlist |
| `tailor-application` | Selected posting, resume/evidence, requested output set; experience questions when needed | Resume and/or cover letter, requirement matrix, claim evidence, gap report, inspectable checks |
| `record-application` | Selected opportunity, explicit user action, date/notes, selected document versions | Application event and rebuildable current status |
| `prepare-interview` | Selected opportunity or role, research, experience evidence, interview stage/format | Preparation material, practice notes, feedback, unanswered questions |

Preferences and experience capture are shared services used by these graphs;
they do not require a giant mandatory onboarding graph. Initial role research
can run before a resume is supplied. Job discovery asks for location/remote,
seniority, sponsorship needs, compensation priorities, and exclusions only
when those answers matter. Tailoring asks for the requested documents and
evidence needed to support claims. Interview preparation asks about its stage
and format when those are unknown.

Missing, explicitly declined, optional, and answered inputs remain distinct.
Hard requirements and preferences remain distinct. In particular, unknown
sponsorship support is not evidence that an employer sponsors or does not
sponsor, and a role title does not establish the candidate's experience.

Research may lead to more research, a saved experience answer, tailoring, or
interview preparation. Suggestions for a next graph do not execute it. The
agent can help select earlier artifacts; GigAI records exactly which versions
become the next Run's inputs. No graph receives every previous Run by default.

## Persistence, customization, and portability

- Store reusable user data as private, revisioned records. A current-profile
  projection may resolve the latest selected revision; a Run pins the resolved
  revisions so later edits cannot change its historical inputs.
- A task-only override, such as including New York for one search, is distinct
  from updating a saved relocation preference. The agent exposes the scope of
  an update when it is ambiguous.
- Preserve original imported material. New answers, documents, and research
  create new records or revisions with parent references; they do not rewrite
  earlier evidence.
- Keep portable template definitions and supporting source code separate from
  private user records, transcripts, application data, credentials, and Runs.
  Supporting code requires declared inventory, version, invocation, and effects;
  initialization or package inspection never executes it implicitly.
- Permit explicitly selected conversation messages, Q&A, summaries, and
  session references with honest source labels. A summary is not an exact
  transcript. Do not harvest unrelated sessions or claim hidden reasoning is
  available.
- Preserve template provenance and user customization lineage. Updating the
  template offers a reviewable comparison and explicit adopt/defer behavior;
  it must not overwrite user edits or private data.
- Distinguish sharing a reusable template from transferring one's own private
  workspace. The latter requires an explicit private backup/restore contract
  with destination checks and no credential copying. It is not catalog export.

## Deferred scope and authority

This release does not include application submission, recruiter outreach,
email sending, interview scheduling, unattended discovery, background agents,
automatic application-state inference, a GigAI-owned Exa broker, or hidden
reasoning capture. Rich document export is not assumed: SCOUT-00 must name the
actual supported formats and avoid presenting a Markdown check as a PDF/DOCX
parser test. Arbitrary plugin execution and automatic dependency installation
are outside the supporting-code contract.

Approval of this roadmap authorizes the coordinator to implement its goals,
write the necessary bounded contract amendments, dispatch/review workers,
resolve routine implementation decisions, and perform agreed verification.
It does not retroactively activate old broker goals, grant user-specific
provider disclosure, redeem GigAI Run consent, supply missing personal facts,
or authorize publication. Existing historical artifacts and user work remain
preserved. Material changes beyond this release outcome return to the user.
