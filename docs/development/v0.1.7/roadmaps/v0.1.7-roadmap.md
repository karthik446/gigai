# GigAI v0.1.7 Roadmap

**Date:** 2026-08-24
**Status:** Proposed; not implementation authority
**Baseline:** v0.1.6 / `main` at `7f9ceb5`
**Release rule:** Every goal in this roadmap is part of the complete v0.1.7
release. The sequence defines dependency order, not optional scope or a reduced
vertical slice.

## v0.1.6 -> v0.1.7 product amendment

v0.1.7 is an intentional product-surface amendment to v0.1.6, not a routine
feature expansion.

v0.1.6 carried a browser-first onboarding and setup direction, including an
HTMX-backed path for setup, creation, approval, and operator interaction. That
direction is retired by this roadmap. It made ordinary setup dependent on a
second interaction surface even though the invoking agent already operates in
the terminal, made clean-environment setup harder to diagnose, and separated
the user's configuration conversation from the local runtime and authority
facts GigAI must own.

The v0.1.7 pivot makes the terminal the primary product surface:

- the agent remains the conversational front door and configuration partner;
- GigAI provides seamless local runtime discovery and a compact CLI setup;
- proposal, approval, Run control, review inspection, and reporting are
  available through CLI, JSON, Markdown, and durable local evidence; and
- no parallel setup or approval surface may create a competing state or
  authority path.

This amendment changes the interaction surface, not GigAI's authority model.
Existing configuration, registry, journal, workpad, proposal/version,
capability, and Run authorities remain the basis of the release. The
repository-wide reconciliation gate below records the exact v0.1.6 statements
and defaults that must be replaced before implementation acceptance.

## Release decision

v0.1.7 is the complete CLI-first pivot from an agent conversation to a durable
GigAI workflow. The invoking agent remains the conversational front door and
configuration partner. GigAI owns local runtime facts, validation, proposal
and version authority, approval, Runs, evidence, review state, and reuse.

The release must support the complete path:

```text
agent CLI
  -> seamless local runtime discovery
  -> CLI setup and explicit configuration choices
  -> agent-backed Gig proposal
  -> GigAI validation and explicit approval
  -> immutable Gig/version authority
  -> bounded adaptive Run Plan
  -> Run execution and evidence
  -> review, reporting, portability, and human UAT
```

The release is not complete if setup is not CLI-native, Gig creation still
requires `InterviewHTTPServer`, approval works only through a library
workaround, or the runtime collapses detection into readiness.

## Product surface

### Required in v0.1.7

- CLI-first setup, configuration, discovery, doctor, proposal, approval, Run
  control, status, and evidence inspection;
- seamless local discovery of supported agent CLIs from the effective
  login-shell environment, including executable, version, runtime identity,
  and bounded failure evidence;
- Codex and Claude adapter startup, readiness, authentication-required
  reporting, cleanup, and provider-preserving failure classification;
- project-local `.gigai/` packages with portable definitions separated from
  private execution material;
- a built-in catalog of useful Gigs and normal Gig/version authority;
- agent-backed Gig creation, clone, and create-from flows with explicit
  questions, consent, validation, proposal persistence, and approval;
- adaptive review profiles and bounded VAR-shaped orchestration with explicit
  role/model assignments and sealed Run Plans;
- reference and research workflows, domain Gigs, background Runs, and
  rebuildable CLI/JSON/Markdown reporting;
- held-out quality, security, portability, no-fallback, footprint, recovery,
  and human-UAT evidence; and
- a final release decision based on the complete workflow, not isolated
  command demonstrations.

The v0.1.7 product surface is CLI, JSON, Markdown, and durable local evidence.
Setup, Gig creation, approval, Run control, review inspection, and reporting
must be complete through those surfaces. The release does not define a second
presentation or authority path.

The product boundary also requires that Orca remain research evidence rather
than a GigAI dependency, that remote execution hosts receive a separate
contract, that agent input be explicitly invoked and typed, and that provider
fallback, silent retry, unbounded scanning, hidden transcript import, and
unconsented background effects remain disallowed.

## Authority invariants

The roadmap does not create a new authority model. Every goal must preserve:

- configuration as machine configuration authority;
- the registry as project/workpad target-binding authority;
- proposal data as non-authoritative until explicit approval;
- the journal and workpad as lifecycle and active-version authority;
- capability manifests and effect policy as capability authority; and
- sealed Run manifests, Run details, and content-addressed artifacts as
  execution and evidence authority.

Discovery snapshots, readiness probes, CLI projections, agent events, reports,
and future renderers are evidence or projections. They may not approve a Gig,
select an active version, create a Run, mutate a target, or adjudicate a
review.

## Research gates already resolved

### S40 — CLI-first seamless local runtime

S40 is the completed Orca research finding. It established that the useful
runtime evidence is bounded login-shell PATH hydration, a closed command
catalog, real executable resolution, bounded install-directory fallback,
runtime identity, and observational status separation. Orca remains research
evidence and a possible future host, not a GigAI dependency.

### S41 — CLI-only runtime seam and Gig-creation UAT

S41 is complete with terminal outcome **ADOPT WITH AMENDMENT**. It is a
completed research gate, not an implementation goal.

S41 requires the implementation lane to provide:

1. a GigAI-owned local runtime discovery snapshot;
2. seamless PATH hydration and bounded executable discovery;
3. structured setup and readiness failures rather than tracebacks;
4. a complete, tested CLI approval authority transition;
5. an HTTP-free, agent-backed Gig-creation seam;
6. distinct detected, configured, compatible, authenticated, verified,
   usable, and selected states; and
7. preservation of all existing journal, workpad, proposal/version,
   capability, and Run authorities.

S41 establishes the CLI, JSON, Markdown, and durable-local-evidence boundary
for the implementation lane. Orca UI, plugins, skills, WSL/SSH forwarding,
and status-derived authority are not part of GigAI's local runtime contract.

## Goal contracts

Each goal below requires its own reviewed contract before implementation. The
roadmap names the contract boundary; it does not activate the goal or replace
its acceptance evidence.

### G40 — Seamless local runtime and CLI adapters

**Depends on:** S40 and S41; existing v0.1.6 configuration, adapter, lifecycle,
journal, workpad, and Run authorities.

**Owns:**

- GigAI-owned discovery snapshots with runtime identity, effective PATH source,
  executable path, version evidence, refresh, timestamp, and bounded failure;
- login-shell PATH hydration and narrowly bounded install-directory fallback;
- closed Codex/Claude runtime catalog and real-executable resolution;
- explicit separation of detected, configured, compatible, authenticated,
  verified, usable, and selected states;
- `setup`, `models`, and `doctor` as CLI/JSON/Markdown surfaces;
- structured clean-environment diagnostics;
- adapter startup, readiness probes, timeout and cancellation behavior,
  provider identity, and orphan cleanup;
- CLI-native setup with structured configuration and readiness diagnostics; and
- the agent-facing command/JSON seam needed by later Gig creation.

**Does not own:** project package authority, built-in Gig definitions, adaptive
review policy, quality acceptance, or background scheduling.

**Acceptance evidence:** clean and altered PATHs; noisy and failing shells;
missing, aliased, and user-local executables; version timeout and malformed
output; refresh after installation; authentication-required versus missing
executable; safe environment and process cleanup; structured diagnostics; and
CLI setup and command help that work in a clean environment without an
implicit presentation process.

#### S41 failure carry-forward

The following unresolved S41 results are G40 blockers, not informational
limitations:

| S41 result | G40 required change | Required acceptance evidence |
|---|---|---|
| Clean non-interactive setup raised `ValueError` for missing `--editor` | Make setup choose safe defaults or return a typed diagnostic with stable exit behavior | Clean-home setup succeeds or emits structured JSON/terminal diagnostics with no traceback |
| CLI approval raised `TypeError` because `capability_manifest_id` was absent from the command contract | Align the CLI declaration and implementation, then invoke the existing lifecycle authority through the CLI | CLI approval alone creates the approved version; direct library invocation is not accepted as a workaround |
| Standard creation still instantiated `InterviewHTTPServer` | Define and implement the explicit agent-backed CLI/JSON invocation seam | A proposal can be configured, validated, persisted, and approved through the agent envelope without `InterviewHTTPServer` |
| Codex probe hit a host permission failure and Claude reported authentication required | Preserve provider identity and distinguish host failure, authentication, and readiness | Each condition is reported as its own bounded state with no fallback or false usability |

### Agent invocation contract

G40 must define the exact typed envelope consumed by later G44 creation and
G49 UAT. The contract must include:

- explicit triggers: `gigai:`, `$gigai`, `/gigai`, or `gigai run`; ordinary agent
  conversation is never inferred as GigAI intent;
- `protocol_version`, `invocation_id`, `actor`, `command`, `input`, and
  target/workpad identity;
- actor identity sufficient to distinguish the invoking agent, the local user,
  and GigAI's validation/authority process;
- a bounded intent or proposal input, requested roles/models/capabilities,
  and explicit consent records; and
- a refusal result for missing triggers, malformed envelopes, unsupported
  fields, missing consent, or unauthorized effects.

The invoking agent is the interviewer and configuration partner. GigAI is the
deterministic validator, proposal/version authority, approval boundary, and
evidence writer. The envelope must not contain the surrounding conversation,
hidden prompt text, raw transcript, credentials, or ambient repository state.
User consent is required before proposal approval, capability installation,
network access, target mutation, or Run execution. The agent cannot approve
its own proposal.

### G41 — Project-local `.gigai/` package boundary

**Depends on:** G40.

**Owns:** repository-root detection, explicit idempotent `gigai init`, package
manifests, portable Gig definitions, selective ignore rules, and separation of
portable material from private `local/`, `runs/`, `cache/`, `snapshots/`, and
secret material.

**Acceptance evidence:** Git and non-Git targets; nested repository handling;
repeated init; refusal and rollback; portable package inspection; reinstall in
a second home; no credentials, absolute paths, private Runs, caches, installed
tool bytes, or automatic install/execute hooks in portable material.

G41 also owns the v0.1.6-to-v0.1.7 upgrade contract. Upgrade evidence must
prove preservation of existing configuration, Gigs, approved versions,
journals, workpads, and Runs; idempotent migration; recoverable backup or
staging; refusal before partial authority changes; and rollback that leaves the
v0.1.6 state readable when migration cannot complete. Fresh-install evidence
alone does not satisfy G41.

### G42 — Built-in Gig catalog

**Depends on:** G40 and G41.

**Owns:** portable built-in definitions for `sync-references`,
`plan-a-research`, `review-plan`, and the initial standard pack, all installed
through the normal proposal/version/capability authority model.

**Acceptance evidence:** catalog listing and identity; package portability;
installation and update idempotence; schema and capability validation; source
immutability; explicit approval; and successful use through the ordinary Run
path.

### G43 — Adaptive review profiles and sealed Run Plans

**Depends on:** G40, G41, and G42; consumes accepted review/evaluation
evidence from the old branch only after audit.

**Owns:** task and artifact classification, typed review profiles, bounded
Review → Verify → Adjudicate → Resolve routing, role/model assignments, human
override, abstention on ambiguity, hard ceilings for calls/passes/loops/wall
time/usage, and sealed Run-Plan preparation.

**Acceptance evidence:** deterministic routing fixtures; ambiguous and rejected
classification; human override; no hidden escalation or fallback; profile
budget enforcement; sealed plan reconstruction; provider identity; role
assignment evidence; and unchanged active-version and Run authority.

### G44 — Clone and create-from

**Depends on:** G41, G42, and G43.

**Owns:** immutable source selection, new identity or explicit child lineage,
agent-configured draft differences, proposal validation, user feedback,
approval, and creation of exactly one new approved version.

**Acceptance evidence:** clone versus create-from identity rules; invalid
fields/capabilities/effects; cancellation and rollback; source immutability;
repeat requests; proposal-to-version lineage; explicit approval; and no
transcript capture or model-controlled approval.

### G45 — Reference and research workflows

**Depends on:** G40, G41, G42, and G43.

**Owns:** repository classification, reference coverage, immutable snapshots,
provenance, evidence collection, research planning, and CLI/JSON/Markdown
reports that cite exact source and artifact identities.

**Acceptance evidence:** local reference selection; missing and changed input;
snapshot digest verification; sanitized provenance; no ambient repository
scan; bounded network policy; evidence rebuild; and reproducible report output.

### G46 — Domain Gigs and evaluation packs

**Depends on:** G42, G43, and G45.

**Owns:** the initial domain Gigs for stock analysis, job preparation, article
fact-checking, document review, code/repository review, and research review,
each with an explicit evaluation pack and honest capability boundary.

**Acceptance evidence:** one contract and fixture pack per Gig; held-out tasks;
quality and failure reports; usage and latency measurements; no claim that one
Gig's evidence proves another Gig's quality; and normal approval/Run lineage.

Each evaluation pack must freeze its acceptance protocol before held-out
execution. It must define:

- development/calibration versus held-out splits, with no held-out tuning;
- the task-level rubric, label schema, minimum quality score, and minimum
  passing-task rate;
- the independent human-label and adjudication procedure where quality needs
  human judgment;
- maximum calls/tokens or provider budget and the accounting method;
- maximum and percentile wall-time limits, timeout treatment, and failure-rate
  limits; and
- reproducibility criteria for fixtures, contract identity, routing, evidence,
  and report reconstruction. Model text need not be byte-identical, but the
  accepted structure and provenance must be reproducible.

G46 cannot claim acceptance when any required threshold, split rule, label
protocol, cost measure, latency measure, or reproducibility check is absent.

### G47 — Background Runs and CLI/Markdown reporting

**Depends on:** G40, G43, G45, and G46.

**Owns:** bounded background workers, startup/shutdown, orphan recovery,
explicit cancellation, Run detail, multi-model call-chain evidence, and
rebuildable CLI/JSON/Markdown reports.

The worker is not a second authority. It consumes a sealed Run Plan and writes
Run evidence through the existing Run lifecycle. It does not add scheduler
policy, silent retry, or hidden provider activity to v0.1.7.

**Acceptance evidence:** foreground/background equivalence; bounded worker
footprint; restart and orphan recovery; cancellation; failure terminalization;
call-chain reconstruction; usage and failure evidence; report rebuild; and no
duplicate Run or active-version authority.

### S48 — Per-Gig quality, security, portability, and footprint gate

**Depends on:** all implementation goals G40–G47.

**Owns:** release-wide evaluation and security evidence, held-out quality,
portable-package checks, no-fallback proof, credential and transcript privacy,
resource/idle footprint, recovery, and operator evidence completeness.

**Acceptance evidence:** every release Gig has a held-out pack; mutation and
negative tests cover authority and fallback boundaries; provider failures are
honest; portable packages are clean; background idle activity is measured; and
the complete CLI path is replayable in a clean environment.

### G49 — Human UAT and v0.1.7 release decision

**Depends on:** S48.

**Owns:** final operator UAT, release checklist, known-limitations record,
version/release evidence, and the explicit release decision.

The primary UAT must be executable from a terminal:

```text
clean environment
  -> gigai setup
  -> gigai doctor / models
  -> agent invokes GigAI
  -> configure and validate proposal
  -> explicit approval
  -> select bounded review profile
  -> seal and run
  -> inspect CLI/JSON/Markdown evidence
  -> repeat or report failure
```

The UAT must include Codex and Claude where the host permits, plus deterministic
fixtures for unavailable, unauthenticated, incompatible, cancelled, timed-out,
and provider-failed cases. Host limitations are recorded; they are never
converted into false readiness or hidden fallback.

## Release-wide stop conditions

The release lane stops and records a failed or blocked gate if:

- setup is not CLI-native or ordinary Gig creation still requires `InterviewHTTPServer`;
- a local runtime snapshot becomes a second configuration or Run authority;
- detection is presented as authentication, compatibility, verification, or
  usability without the corresponding evidence;
- CLI approval cannot prove the proposal-to-version authority transition;
- an agent can inject hidden prompts, import ambient transcript, or approve its
  own proposal;
- a worker silently retries, falls back, escalates budgets, or starts provider
  activity without recorded consent;
- portable packages contain credentials, private Runs, caches, absolute paths,
  installed tool bytes, or automatic hooks;
- review routing cannot abstain or respect bounded profile limits;
- reports cannot be rebuilt from authoritative local artifacts; or
- human UAT cannot complete the complete CLI workflow with honest failure
  outcomes.

## Roadmap governance

This document is the proposed v0.1.7 roadmap. It becomes implementation
authority only after human review accepts the release boundary, dependency
graph, carry-forward dispositions, and G40 contract entry point.

Until then:

- S40 and S41 remain completed research evidence;
- no runtime implementation is authorized by this document;
- each G40–G49 contract must be written and reviewed under
  `docs/development/v0.1.7/goals/` before implementation; and
- changes to this roadmap must preserve the complete-release rule and the
  CLI, JSON, Markdown, and durable-local-evidence product surface.
