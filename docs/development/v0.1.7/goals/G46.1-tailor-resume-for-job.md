# G46.1 — Job Search Lifecycle Gig v1: `tailor-application`

**Version:** v0.1.7
**Status:** Proposed — contract defined; not activated
**Parent:** G46 Job Search Lifecycle Gig family and evaluation packs
**Depends on:** G43.2, G45, and G46 complete and ratified
**Delivery:** private foreground dogfood Gig; not a G42 catalog entry
**Previous working name:** private `tailor-resume-for-job`

## Outcome

G46.1 proves the first complete private Job Search Lifecycle workflow with
material that matters to an operator. It creates, approves, plans, runs,
reviews, and inspects a reusable `tailor-application` graph in Job Search
Lifecycle Gig v1 while keeping résumé material private and the original résumé
untouched.

```text
private resume/project references + pasted job description
  -> agent-assisted private Gig proposal
  -> explicit operator approval
  -> G43 standard@1 Run Plan
  -> direct-confirmed foreground Run
  -> private tailored artifacts and evidence
  -> operator factuality/usefulness review
```

This is the first named implementation track under G46. It is not a new
top-level roadmap goal, a built-in catalog entry, a job-board client, or an
application-submission tool. A later v2 may add the separate
`find-jobs-for-requirements` graph; that does not make job discovery an input
or effect of this v1 graph.

## Stable definition and changing inputs

The stable Gig definition declares a truthful job-tailoring workflow:

1. normalize the supplied job description without replacing its snapshot;
2. extract role responsibilities, qualifications, and evidence signals;
3. map each material requirement to supported résumé/project evidence, an
   explicit gap, or `not_applicable`;
4. select only supported experience, skills, and achievements for emphasis;
5. write the requested private application material; and
6. review the artifacts against the job description, evidence map, and
   no-invention constraints.

Stable constraints are: preserve source material; do not invent experience,
dates, employers, titles, education, certifications, projects, skills,
metrics, outcomes, or qualifications; disclose unresolved gaps; and never
submit an application or contact a third party.

Each Run names exactly one G45 `job_description` input. Stable private
references consist of at least one `resume` and optional `project_evidence`,
`role_history`, or `cover_letter` records. No ambient file, previous Run,
agent conversation, URL, or unselected reference is input to this Gig.

G46.1 declares G43 task class `document_review` and artifact class `mixed`:
the plan reviews and rewrites multiple declared text artifacts without treating
the surrounding project as input. These explicit Gig declarations take
precedence over classifier heuristics. The required effects are private
workpad reads/writes and, only for the selected configured provider, the
already-consented model invocation boundary. It requires no target read/write,
job-source network read, external write, or package effect.

## Operator questions and output contract

The agent may ask only bounded questions needed to form the proposal or Run:

- desired outputs: tailored résumé, cover letter, or both;
- target role/title, if it is not clear from the supplied posting;
- requested tone: conservative, direct, or tailored;
- optional experiences or projects to emphasize, named by private reference;
- whether a cover letter is requested; and
- whether the operator wants an explicit gap report (default: yes).

Missing required information produces a typed refusal or a bounded question;
the agent does not infer it from surrounding conversation. The operator reviews
the resolved inputs and output set before approval and again before the Run.

Every successful Run writes private workpad artifacts:

- `runs/<run_id>/outputs/requirements-matrix.md` with each material job
  requirement classified as
  `supported`, `gap`, or `not_applicable`, with reference IDs/digests;
- `runs/<run_id>/outputs/tailored-resume.md` when requested;
- `runs/<run_id>/outputs/cover-letter.md` when requested;
- `runs/<run_id>/outputs/gap-report.md`, including every material unresolved or unsupported
  qualification; and
- `runs/<run_id>/outputs/claim-evidence.json` and
  `runs/<run_id>/outputs/output-manifest.json`.

The four Markdown files use the existing strict handoff front matter plus a
private body. `resume-output-manifest.schema.json` has schema ID
`urn:gigai:schema:resume-output-manifest:1`, schema version `1.0`, and requires
`schema_version`, `output_manifest_id`, `run_id`, `gig_id`,
`requirements_matrix`, `tailored_resume`, `cover_letter`, `gap_report`,
`claim_evidence`, `status`, and `created_at`. Every output artifact field is an
existing artifact reference or null only for an unrequested résumé/cover letter.
`output_manifest_id` matches `resume_output_<uuidv4>` and `status` is exactly
`complete`, `blocked`, or `operator_required`. The semantic validator requires
the non-null artifact paths listed above, exact digest agreement, and both
requirements matrix and gap report for every completed Run.

Outputs are drafts, not application-ready truth by assertion. The operator
must review them before copying, exporting, or using them. G46.1 does not
overwrite a source résumé, modify a target repository, generate DOCX/PDF,
send email, fill a website, or submit an application.

## Factuality and provenance rules

Every material factual claim about the operator in every output artifact must
have one or more exact private source references in the claim-evidence record.
That includes first-person sentences, third-person prose, résumé fragments,
bullets, headings, metrics, titles, dates, skill lists, and implied ownership
claims such as “Led migration…”. Paraphrase and reordering are allowed only
when they preserve the referenced meaning. Job-description language may
describe the target role but never becomes evidence that the operator has a
skill or experience.

`resume-claim-evidence.schema.json` is private, strict, schema ID
`urn:gigai:schema:resume-claim-evidence:1`, schema version `1.0`, and stored at
`runs/<run_id>/outputs/claim-evidence.json`. It requires `schema_version`,
`claim_evidence_id`, `run_id`, `gig_id`, `claims`, and `created_at`.
`claim_evidence_id` matches `claim_evidence_<uuidv4>`. Every claim has unique
`claim_id` matching `resume_claim_<uuidv4>`, an `output_artifact` reference, a
`locator`, `claim_kind`, `claim_status`, `verification_status`, `source_refs`,
and nullable `gap_reason`. A locator is exactly `{ "start_line": positive
integer, "end_line": positive integer }`, with `end_line >= start_line` in
the digest-pinned output artifact. `claim_kind` is `operator_factual` or
`job_requirement`; `claim_status` is `supported`, `gap`, `not_applicable`,
`unsupported`, or `operator_required`; and `verification_status` is
`unverified`, `verified`, `contradicted`, or `blocked`.

`operator_factual` claims marked `supported` require one-or-more source
artifact references; all other `operator_factual` statuses require an empty
source-reference array and, except `not_applicable`, a non-empty gap reason.
The semantic validator rejects a claim whose artifact path is outside the
output manifest, whose locator is outside the exact output bytes, or whose
source reference is not one of the sealed G45 inputs. The record stores
locators and content digests rather than copying the claim or source text into
diagnostics, reports, fixtures, or portable material. The requirements matrix
uses the same source references and its three-state vocabulary.

When evidence is absent, contradictory, or too vague, the writer must omit the
claim from application material and record a `gap` or `operator_required`
result. The verifier checks every material factual claim and may not erase the
source finding. The resolver may choose `inconclusive`, `blocked`, or
`operator_required`; it cannot convert an unsupported claim into an accepted
one.

The original imported snapshot's digest is recorded before and after the Run.
Any changed, unreadable, foreign-project, or mismatched source blocks the Run
before output generation.

## Profile and provider policy

G46.1 requires G43 `standard@1`; `focused@1` is not permitted because its
single participant is explicitly non-independent. The plan uses G43's two
reviewers, verifier, adjudicator, deterministic resolver, limits, and direct
Run-consent handoff.

For provider-backed UAT, both reviewer participants must use two distinct
usable configured model targets. The plan records every role-to-target mapping
and whether a target is reused for verifier or adjudicator. Two targets prove
multi-model review, not target-disjoint verification. A report may claim an
independent verifier target only when the verifier target differs from both
reviewer targets; that requires a third usable target. There is no silent
fallback or role reassignment when a selected target is unavailable.

The operator may explicitly choose eligible targets and profile only within
the G43 limits. The configured G43 budget for `standard@1` is the upper
envelope; G46.1 may reduce it but may not increase calls, tokens, cost, or wall
time. Every provider call, model target, usage record, failure, and target
reuse is durable Run evidence.

G46.1 fixes G43 `usage_unreported_policy` to `block_before_call`. If the
selected target cannot supply token usage, or cannot supply either
provider-reported cost or a configured derivation table, the Run records
`usage_unavailable` or `cost_unavailable` and refuses before the first provider
call. G46.1 never
uses `reserve_remaining_budget`; that option remains available only to a later
Gig whose reviewed contract deliberately accepts its accounting limitation.

## Lifecycle and command path

G46.1 uses the normal CLI-first lifecycle rather than a special résumé path:

```text
explicit agent invocation -> gigai create job-search-lifecycle
  -> inspect proposal -> gigai approve
  -> select graph tailor-application and explicitly add/select G45 reference
     and job-input IDs
  -> gigai run-plan create --gig GIG_ID --graph tailor-application
     --profile standard@1 --input INPUT_ID
  -> inspect exact PLAN_ID
  -> gigai run --plan PLAN_ID --confirm
  -> inspect private Run artifacts
```

The agent submits only the bounded G40 invocation envelope. It cannot include
raw résumé/job text as hidden prompt content, approve the Gig, select an
unusable target, grant a capability, or consent to the Run. Approval remains
proposal/version authority; the final direct `--confirm` remains Run consent.

G46.1 creates one private project Gig through the ordinary proposal and
approval lifecycle. It does not copy anything into G42, install a catalog
package, or promote the Gig for other projects. Promotion is a later, explicit
decision after privacy, factuality, and evaluation evidence is reviewed.

## Evaluation pack and UAT

The evaluation pack contains only synthetic or fully sanitized résumés, project
notes, and job descriptions. It has six development/calibration cases and
three held-out cases; the split, expected requirements matrix, and human-label
rubric are frozen before provider-backed held-out execution.

The hard acceptance gates for every held-out case are:

- zero unsupported material factual claims in any output form;
- unchanged source-snapshot digest;
- every material job requirement represented as `supported`, `gap`, or
  `not_applicable` with provenance;
- requested artifacts produced only from declared sources;
- no external effect, target mutation, URL fetch, or catalog/package write;
- a valid G43 standard Run Plan, fresh direct consent, and reconstructable Run
  evidence; and
- provider, model target, usage, cost, wall time, failure condition, and any
  target reuse recorded without credential or raw-reference disclosure.

Independent human review labels factuality, requirement coverage, usefulness,
clarity, and gap honesty on a 1–5 rubric. Held-out acceptance requires a mean
of at least 4 for usefulness and clarity, no factuality or gap-honesty score
below 4, and unanimous agreement on the no-invention gate. A provider failure,
timeout, unavailable target, or unresolved disagreement is an honest failed or
inconclusive case, never a silent retry or pass.

The private foreground UAT uses one real résumé and one pasted job description
only after the synthetic evaluation path works. Its committed evidence contains
only sanitized IDs, digests, command outcomes, aggregate usage/latency, and
operator findings. It must not contain a résumé, job description, raw output,
prompt, credential, absolute personal path, or private workpad contents.

## Acceptance evidence

G46.1 is complete only when it proves:

- agent-backed creation, explicit approval, G43 plan inspection, direct Run
  confirmation, and private output inspection through the normal CLI path;
- required versus optional input enforcement and refusal for missing/changed
  G45 records;
- correct standard-profile role assignment, provider availability behavior,
  target-reuse disclosure, and no fallback;
- source-grounded claim evidence, no-invention failures, and explicit gaps;
- intact original snapshots and no target/external mutation;
- deterministic/sanitized development and held-out evaluation evidence with
  the frozen rubric and thresholds above; and
- one private foreground human UAT recording usability, factuality, known
  limitations, and whether the operator would trust the draft as a starting
  point rather than an unreviewed submission.

## Out of scope

- catalog publication, cross-project reuse, clone/create-from, or G42 changes;
- job URLs, job-board crawling, browser automation, external network reads,
  PDF/DOCX conversion, or OCR;
- application submission, recruiter outreach, email, external writes, or
  target mutation;
- background Runs, scheduling, retries, automatic export, PDF/DOCX rendering,
  or release-wide reporting; and
- claims that synthetic fixtures prove real-world hiring outcomes or provider
  quality outside this Gig.

## Stop conditions

G46.1 must stop and remain incomplete if an unsupported claim reaches an output
artifact, raw private material reaches a package/fixture/committed record, a
selected provider target is silently substituted, approval or Run consent is
inferred from the agent, the source résumé changes, a Run performs an external
effect, or the operator cannot inspect the evidence needed to reject a draft.
