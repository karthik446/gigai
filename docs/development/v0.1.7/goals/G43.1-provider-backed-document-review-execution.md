# G43.1 — Provider-Backed Document Review Execution

**Version:** v0.1.7
**Status:** Active — implementation in progress; public provider dogfood pending
**Depends on:** G40 and G43 complete and ratified; an approved Gig and a
sealed G43 Run Plan
**First dogfood input:** G44 intent-routing and Gig-candidate contract

## Outcome

G43.1 turns a sealed G43 review bridge into one bounded, provider-backed
document-review pass. It is deliberately not a general agent scheduler and it
does not alter Gig, approval, Run, or consent authority.

```text
approved Gig + explicit UTF-8 text/Markdown input
  -> sealed G43 plan and direct `gigai run --confirm`
  -> exact selected input snapshots only
  -> configured reviewer targets execute independently
  -> typed model findings and invocation evidence
  -> configured verifier target evaluates each finding
  -> terminal review report: clean, findings, blocked, or inconclusive
```

The first delivery executes exactly one review/verification cycle. A fix and
re-review are a fresh explicit Run Plan and Run; G43.1 does not let a model
rewrite the reviewed input, mutate the target repository, or silently begin a
second cycle.

## Boundary

Only an existing G43 Run Plan with task class `document_review` or
`planning`, artifact class `text` or `mixed`, and one-to-six explicit UTF-8
`text/plain` or `text/markdown` input snapshots is eligible. The executor
reads only input artifact bytes pinned by that plan. It neither scans the
working tree nor reads an agent transcript, prior Run, clipboard, or an
unselected workpad artifact.

The existing direct `gigai run --plan PLAN --execute-review --confirm` consent
is the only authorization to invoke the model targets sealed in the plan. A
later command may observe the result but cannot add a target, retry a
participant, or broaden the selected input set. Provider unavailability,
invalid model output, missing usage/cost, or a digest mismatch terminalizes the
review as `blocked` or `inconclusive`; there is no fallback.

G43.1 does not add tool use, network research, web browsing, target effects,
background scheduling, autonomous fixes, prompt optimization, or user-data
classification. The configured provider invocation boundary remains the G18
model-execution seam.

## Final G44 dogfood input contract

The final public G44 dogfood Plan is a typed two-input review, not a generic
one-input document check. Its sealed `inputs` array contains exactly one record
with each of these roles:

- `review_subject` — the public G44 contract being assessed; and
- `requirements_baseline` — the separately frozen, operator-approved public
  requirements artifact against which that subject is assessed.

The two snapshots must be distinct, valid UTF-8 Markdown/text artifacts. The
`record_ref` for each role is a new strict
`urn:gigai:schema:review-input-record:1` artifact. It requires
`schema_version`, `review_input_id`, `role`, `snapshot_ref`,
`approval_state`, `approved_by`, and `approved_at`.
`review_input_id` matches `review_input_<uuidv4>`, `role` is exactly
`review_subject` or `requirements_baseline`, and `approval_state` is exactly
`not_required` or `operator_approved`. A `review_subject` record uses
`not_required` with null approval fields. A `requirements_baseline` record
uses `operator_approved` with a non-null operator actor and timestamp. Its
`snapshot_ref` and the enclosing Plan's `snapshot_ref` must be byte-identical.

Both records and both snapshots are sealed sources in the Plan. The baseline
is never inferred from the subject, proposal status, surrounding repository, or
provider prompt.

Plan creation and provider-review execution refuse with stable diagnostics when
the required role set is absent or duplicated (`review_input_roles_invalid`),
the baseline is unapproved (`requirements_baseline_unapproved`), its sealed
snapshot is missing or differs (`requirements_baseline_missing` or
`requirements_baseline_changed`), or the subject/baseline was not separately
sealed (`review_input_not_sealed`). A normal one-input G43.1 review remains
eligible for its existing bounded use cases; these two roles are mandatory only
for the G43.1 closure dogfood identified by this Goal.

For that dogfood, the generated review contract includes
`criterion_requirements`, whose normative source is the
`requirements_baseline` snapshot. Its `reference_roles` are exactly
`review_subject` and `requirements_baseline`, and its required evidence is
exactly both roles. Reviewer prompts label the two artifacts as **Review
subject** and **Requirements baseline**. A finding for that criterion must cite
the baseline locator that states the requirement and the subject locator that
establishes the gap, agreement, or absence. The verifier receives the same
role-labelled snapshots and checks both references; a baseline that is present
but not cited is not evidence of requirements reconciliation.

A fresh closure re-review has a required `re_review_of` binding to the original
Run Plan ID and content digest. The Plan validator loads that original sealed
Plan and requires byte-identical `requirements_baseline` snapshot digests. A
changed baseline raises `requirements_baseline_changed`; it is a new review
scope, not a re-review, and requires a fresh approved baseline, fresh Plan,
and a separately recorded comparison.

## Execution and evidence

For each sealed reviewer participant, GigAI constructs a bounded review prompt
from the existing review contract and asks for JSON findings. The response is
stored exactly as a private model-invocation response artifact. GigAI accepts
only schema-valid finding objects that cite an exact selected input reference
and locator; otherwise that participant is `inconclusive` and its raw response
remains evidence without becoming a finding.

Reviewer participants execute independently and cannot see another
participant's response. The verifier receives only the sealed input snapshots
and the accepted reviewer findings. It writes one
`verification-record.schema.json` artifact whose outcome for each finding is
`verified`, `contradicted`, `unverified`, or `blocked`. G43.1 does not
manufacture consensus: disagreement or an unavailable verifier is visible in
the terminal report.

The executor journals a separate immutable execution set under
`runs/<run-id>/provider-reviews/<run-plan-id>/`; it does not overwrite the
pending bridge under `runs/<run-id>/review/`.  That set contains:

- one `model-invocation` request, response when available, and terminal record
  for each reviewer/verifier participant;
- immutable finding artifacts with `stage: model`;
- immutable verification records;
- a trace that links participants and invocation IDs without a hidden
  transcript; and
- its own review bundle, review-loop, report, and terminal result artifact.

It must validate every artifact with the existing schemas before publication.
The bridge artifacts written by G43 remain readable and are superseded only by
new versioned evidence, never overwritten as if provider execution had already
occurred.

## Participant and budget policy

The plan's sealed participants, roles, targets, independence groups, and budget
are authoritative. At sealing, `gigai run-plan create` accepts an exact count
of `--reviewer-target`, `--verifier-target`, and `--adjudicator-target` values
in participant order; omitted values use the configured profile mapping. It
refuses a wrong count, an unavailable target, or a pre-call reservation that
cannot cover all sealed participants. `focused@1` may execute its single serial reviewer/verifier
participant but makes no independence claim. `standard@1` dogfood uses two
configured distinct reviewer targets and one verifier target. The first G44
dogfood target mapping is explicitly selected at sealing: Claude Code reviews
and Codex with the Luna model independently reviews; the verifier is a sealed
configured target and any target reuse is reported.

Every call uses the G43 budget reservation and usage/cost policy. If a target
cannot meet the sealed accounting policy, no provider call starts. A successful
reviewer response with no findings needs no verifier or adjudicator call. A
malformed response, provider failure, or missing required response is terminal
`blocked`; GigAI does not synthesize a finding, verification, or adjudication.
Participant
calls are sequential in the initial delivery; the term “independent” concerns
evidence/input isolation, not parallel process scheduling.

## Dogfood acceptance

G43.1 is complete only when a public G44 contract is reviewed through a real
configured Claude target and a real configured Codex-Luna target, with direct
operator consent, and records:

1. an operator-approved public G44 requirements baseline, separately selected
   and sealed alongside the G44 contract; the baseline is review input only and
   does not activate or implement G44;
2. the sealed plan/input digests and selected targets;
3. independent reviewer invocation evidence and typed findings or honest
   terminal failure;
4. verifier evidence and a terminal report;
5. one human-applied G44 correction when a valid finding exists; and
6. one fresh-plan re-review, or an explicit `no_fix_required` record when both
   independent reviews are clean.

Automated tests must cover digest mismatch, unselected input exclusion,
invalid provider JSON, provider failure, usage/cost refusal, target reuse
disclosure, schema replay, and the absence of target-repository effects. They
must additionally cover the exact two-role requirement, duplicate/missing role
refusal, missing/unapproved/changed baseline refusal, role-labelled reviewer
and verifier prompts, criterion findings that bind both baseline and subject
locators, review-input-record schema/semantic validation, `re_review_of`
binding validation, and identical-baseline-digest enforcement across the
original review and its re-review.

## Stop conditions

Stop before provider invocation if exact plan inputs cannot be recovered,
consent is absent, target configuration changed, selected input is not eligible
text, a provider requires an undeclared capability, or the budget policy cannot
be honored. Stop the goal incomplete if a model response can become an accepted
finding without schema validation and exact evidence binding, or if the
implementation turns a provider response into an autonomous fix.
