# G46.2 — Job Search Lifecycle Gig v2: `find-jobs-for-requirements`

**Version:** v0.1.7
**Status:** Proposed — contract defined; not activated
**Parent:** G46 Job Search Lifecycle Gig family
**Depends on:** G44, G45.2, G46, and G46.1
**Delivery:** private operator-started, agent-research foreground graph; not a
catalog entry or scheduler

## Outcome

G46.2 proves an explicitly operator-approved v2 of the private
`job-search-lifecycle` Gig. v2 retains the v1 `tailor-application` graph and
adds one independently selectable `find-jobs-for-requirements` graph.

```text
explicit requirements profile + approved Exa policy
  -> sealed foreground Find Plan
  -> direct-confirmed Codex/Claude Exa research
  -> private, citation-bound job leads and report
  -> operator selects one lead, or stops
```

The graph finds leads that match declared requirements. It does not promise
market coverage, hiring outcomes, application eligibility, or that any lead is
current beyond its recorded retrieval/as-of time.

## Inputs, effects, and outputs

The Find graph accepts exactly one sealed G45.2 `job_search_requirements`
input and one approved Exa research policy. The requirements profile may
contain only the approved query fields plus local filtering preferences: target
role or keywords, location/remote preference, seniority, employment type,
salary constraint when supported, and explicitly named include/exclude
criteria. The operator sees the query brief and every permitted outbound field
before the Plan is sealed. A résumé, private work history, or prior Tailor
output is never an outbound query or implicit input.

Its only external effect is the bounded G45.2 Exa capability. A configured
Codex CLI target performs primary research and a configured Claude Code target
performs independent research/verification under the sealed role-level and
Run-level action budgets. GigAI validates and mediates each typed Exa action;
neither agent receives a generic browser, arbitrary HTTP, credential, or
provider-selection capability. The graph has no target-repository write,
external write, schedule, or submission effect. Returned source text is
untrusted data and cannot override this contract.

Every terminal Run writes private artifacts:

- raw response snapshots and normalized lead records from G45.2;
- `job-leads.json`, `job-leads.md`, and optional rebuildable
  `job-leads.html` projection;
- `job-search-result.schema.json`, schema ID
  `urn:gigai:schema:job-search-result:1`, at
  `runs/<run_id>/outputs/job-search-result.json`; its required fields are
  `schema_version`, `result_id`, `run_id`, `gig_id`, `graph_id`, `exa_policy`,
  `query_brief`, `research_actions`, `provider_usage`, `lead_records`,
  `deduplication_evidence`, `terminal_status`, `diagnostics`, and `created_at`;
  and
- a requirements-to-lead relevance map citing exact requirements and citation
  fields for each result.

HTML is a static Run artifact, not a web server or new authority surface.

## Relevance and quality rules

Relevance is an explanation of the relationship between declared requirements
and cited source fields, not a recommendation, factual claim about the
operator, or inference about application status. Every surfaced reason cites
both a requirements locator and an Exa action/citation-field locator. Missing
fields are displayed as unknown; they are never invented or silently scored as
matches. A Claude verifier must mark a lead unavailable when its supporting
Codex research citation is missing, contradicted, or out of policy.

Within-Run deduplication follows G45.2's identity rule. Cross-Run comparison is
an explicit report operation only in v0.1.7; the graph has no mutable current
lead list, saved list, applied list, or automatic suppression.

The evaluation pack freezes sanitized Exa action/citation fixtures,
requirements profiles, expected normalization/identity outcomes,
relevance-label rubric, no-match/provider-failure cases, and held-out split
before any provider-backed quality execution. It measures provenance
completeness, research-policy compliance, Codex/Claude role separation,
deterministic deduplication, relevance explanation correctness, latency,
Exa/model cost, failure rate, and rebuildability.

## Lifecycle and handoff

G46.2 creates an ordinary Gig amendment from v1 to v2. The operator inspects
the Graph Set difference, Exa research effect, evaluation evidence, and
profile/budget changes, then explicitly approves v2. Existing v1 Tailor Runs
stay attributable to v1 and reproducible.

The operator-started execution path is:

```text
gigai job-requirements add --research-provider exa --stdin
  -> gigai run-plan create --gig GIG_ID --graph find-jobs-for-requirements
       --research-policy exa --input REQUIREMENTS_INPUT_ID
  -> inspect query brief, Codex/Claude assignments, action ceilings, and PLAN_ID
  -> gigai run --plan PLAN_ID --confirm
  -> inspect private lead report
```

After a successful Find Run, `gigai job-lead select LEAD_ID --gig GIG_ID
--confirm` creates the G45.2 lead-input binding. The operator must then create
a separate Tailor Plan naming that binding/input and separately run
`gigai run --plan PLAN_ID --confirm`. There is no automatic Find-to-Tailor
journey in v0.1.7.

## Acceptance evidence and stop conditions

Acceptance proves the v2 graph-addition lineage, independent graph selection,
operator-started Codex/Claude research, Exa action/citation provenance, lead
selection binding, subsequent Tailor Plan binding, and historical v1 replay. It
includes successful research, no matching jobs, stale results, malformed
content, duplicate leads, provider failure, role/Run budget exhaustion,
operator cancellation, unavailable Exa configuration, and refusal of an
unsealed action or undeclared query field.

Stop if an Exa action occurs before direct Run consent, a lead creates or starts
a Tailor Run automatically, private résumé material leaves the selected local
boundary, an agent receives arbitrary web/provider control, application state
is inferred, or an Exa/model failure silently falls back.
