# G46.2 — Job Search Lifecycle Gig v2: `find-jobs-for-requirements`

**Version:** v0.1.7
**Status:** Proposed target contract — not activated
**Parent:** G46 Job Search Lifecycle Gig family
**Depends on:** G43.3 complete and ratified, G44, G45.2 complete and ratified,
G46, and G46.1
**Delivery:** private, operator-started, brokered agent-research foreground
graph; not a catalog entry or scheduler
**Owns:** job-domain field disclosure, relevance, candidate promotion,
selectability, terminal-result algebra, and Find evaluation

## Outcome

G46.2 proves an explicitly operator-approved v2 of the private
`job-search-lifecycle` Gig. v2 retains v1 `tailor-application` and adds one
independently selectable `find-jobs-for-requirements` graph.

```text
sealed requirements + adopted Exa policy + G43.3 research Plan
  -> direct Run confirmation
  -> GigAI-generated public brief -> untrusted Codex research suggestion
  -> GigAI-brokered evidence -> public brief -> untrusted Claude corroboration
  -> G45.2 immutable candidate evidence
  -> G46.2 verified/selectable lead promotion or an honest terminal outcome
  -> optional direct operator lead selection for a separate Tailor Plan
```

The graph finds bounded research candidates for declared requirements. It does
not promise market coverage, hiring outcomes, application eligibility, or that
any posting is current beyond its recorded source time. A candidate is never a
lead recommendation merely because a provider returned it.

## Inputs and outbound disclosure

The Find graph accepts exactly one sealed G45.2 `job_search_requirements`
input and one S45.2-adopted Exa policy reference. The requirements record
contains typed fields for target role/keywords, location/remote preference,
seniority, employment type, salary constraint when chosen, and named
include/exclude criteria. Every field is exactly one of:

- `outbound`: eligible for the adopted policy's request envelope only when its
  value has an exact locator to the sealed requirement snapshot or a sealed
  deterministic transformation; or
- `local_only`: available for local relevance/promotion evaluation only and
  forbidden in every Exa request envelope.

The Plan seals the ordered field list, disclosure class, exact outbound values
or transformations, policy reference, G43.3 participant assignments, and
research budget. GigAI derives a digest-pinned public participant brief only
from the `outbound` fields and renders those exact values to the operator before
direct Run confirmation. Résumé text, private work history, prior Tailor
output, `local_only` requirements, provider responses, agent memory,
diagnostics, and undeclared text are never participant or outbound input.

For the private v0.1.7 UAT, the G43.3 `researcher` is one usable configured
Codex CLI target and `research_verifier` is one different usable configured
Claude Code target. Each receives only its GigAI-generated public brief;
neither participant chooses a broker channel, Run/Plan ID, request, URL,
citation, or provider result. Their target identities, independence groups,
public-brief digests, and per-role ceilings are sealed before consent.
Unavailability of either role yields the defined terminal outcome; it does not
swap roles or substitute a target.

The only external effect is a G43.3-brokered action admitted by the sealed
G45.2 Exa policy. It has no target-repository write, arbitrary URL/browser,
credential, external write, schedule, or submission effect. Source/provider
content is untrusted evidence and cannot change this graph's policy.

## Candidate promotion and lead selectability

G45.2 writes immutable structural candidate records. G46.2 alone may write a
`job-lead-promotion.schema.json` artifact with schema ID
`urn:gigai:schema:job-lead-promotion:1`, at
`runs/<run_id>/job-leads/promotion_<uuidv4>.json`. It requires
`schema_version`, `promotion_id`, `lead_id`, `run_id`, `gig_id`, `gig_version`,
`graph_id`, `candidate`, `discovery_action`, `discovery_participant`,
`verification_action`, `verification_participant`, `evidence_status`,
`promotion_state`, `requirement_matches`, `freshness`, `decision_reason`, and
`created_at`. `lead_id` matches `lead_<uuidv4>` and is populated only for a
`selectable_verified` promotion; the CLI `LEAD_ID` is this field, not a raw
candidate ID.

`evidence_status` is exactly `verified`, `contradicted`, `unverified`, or
`unavailable`. `promotion_state` is exactly `selectable_verified` or
`not_selectable`. `freshness` is exactly `fresh`, `stale`, or `unknown`.
A `selectable_verified` promotion requires:

1. one valid candidate from a GigAI-owned broker action associated with
   participant A's suggestion;
2. one accepted independent GigAI-owned verification action associated with
   participant B's suggestion from a different G43.3 independence group and
   target;
3. citation locators in both action chains supporting the displayed identity,
   role, employer when present, location when present, and job-description
   material used for relevance; and
4. `evidence_status: verified`, `fresh` or explicitly disclosed `unknown`
   freshness, and every surfaced relevance reason tied to an exact requirement
   locator and citation locator.

Candidates associated with a Codex suggestion require a Claude-associated
brokered corroboration action; the reverse applies to Claude suggestions. A
participant-provided finding, URL, citation, or claim is never a candidate.
A participant may suggest additional actions but cannot self-verify the only
broker evidence for one. Contradictory or missing evidence produces
`not_selectable`; it may remain a private diagnostic candidate but must not
appear as a verified lead or Tailor input.

## Terminal-result algebra and outputs

`job-search-result.schema.json` has schema ID
`urn:gigai:schema:job-search-result:1` and is stored at
`runs/<run_id>/outputs/job-search-result.json`. It requires `schema_version`,
`result_id`, `run_id`, `gig_id`, `gig_version`, `graph_id`, `research_plan`,
`policy`, `requirements`, `research_actions`, `provider_usage`, `candidates`,
`promotions`, `terminal_status`, `diagnostics`, and `created_at`.

`terminal_status` is exactly one of the following. Candidate artifacts may
always remain private evidence; “reportable” means a report may disclose a
safe count and status, while “selectable” means eligible for G45.2 direct
operator selection.

| Terminal status | Reportable result | Selectable candidate |
|---|---|---|
| `complete_verified_results` | verified leads and diagnostics | only `selectable_verified` |
| `complete_no_matches` | no matches | none |
| `partial_inconclusive` | unverified diagnostic candidates, clearly labelled | none |
| `provider_unavailable` | unavailable reason | none |
| `provider_failed` | failed reason and safe counts | none |
| `verification_unavailable` | candidates as unverified diagnostics | none |
| `disagreement_unresolved` | contradicted/unresolved diagnostics | none |
| `budget_exhausted` | bounded-progress diagnostics | none |
| `cancelled` | cancellation point and safe counts | none |
| `stale_only` | stale candidate diagnostics | none |
| `malformed_or_policy_rejected` | rejection diagnostics | none |

Only `complete_verified_results` may include a promotion with
`selectable_verified`. If no independent verification completes, no candidate
is equivalent to a verified lead. A partial Run never upgrades an old candidate
or reuses another Run's evidence; a later Run must research and promote again.

Every completed or partial Run writes private `job-leads.json`, `job-leads.md`,
and optional rebuildable `job-leads.html`, plus requirements-to-citation
relevance evidence. HTML is static output, not a web service or authority.
Reports distinguish verified leads from diagnostic candidates and display
`as_of: unknown` literally when the source supplied no authoritative time.

## Lifecycle, consent, and evaluation

G46.2 creates an ordinary approved Gig amendment from v1 to v2. The operator
inspects the Graph Set difference, G43.3 research effect, adopted Exa policy,
outbound-field disclosure, evidence/promotion rules, evaluation evidence, and
budget changes before explicitly approving v2. Existing v1 Tailor Runs remain
attributable to v1 and reproducible.

The operator-started execution path is:

```text
gigai job-requirements add --research-policy POLICY_ID --stdin
  -> gigai run-plan create --gig GIG_ID --graph find-jobs-for-requirements
       --research-policy POLICY_ID --input REQUIREMENTS_INPUT_ID
  -> inspect exact outbound values, G43.3 roles, action budget, and PLAN_ID
  -> gigai run --plan PLAN_ID --confirm
  -> inspect verified leads or the explicit terminal outcome
```

After `complete_verified_results`, `gigai job-lead select LEAD_ID --gig GIG_ID
--confirm` creates a G45.2 binding only for a current `selectable_verified`
promotion. The operator then creates a separate Tailor Plan naming that binding
and separately confirms its Run. There is no automatic Find-to-Tailor journey.

The evaluation pack freezes sanitized requirements, broker/action/citation
fixtures, expected field-disclosure outcomes, candidate/promotion states,
terminal-result outcomes, and held-out split before provider-backed execution.
It measures disclosure correctness, public-brief exclusion, broker/policy
compliance, independent corroboration, citation provenance, relevance
explanation correctness, promotion correctness, deduplication, latency,
Exa/model cost, failure rate, and rebuildability. It must include
suggestion-spoofing attempts, both Codex-associated and Claude-associated
broker candidates, disagreement, one-participant exhaustion, stale-only
evidence, and each terminal status.

## Acceptance evidence and stop conditions

G46.2 is complete only when tests and UAT prove v2 approval lineage,
independent graph selection, field-level outbound disclosure, current G43.3
role/evidence bindings, every promotion rule, every terminal status, explicit
operator selection, separate Tailor consent, and historical v1 replay.

Stop if a candidate becomes surfaced or selectable without G46.2 promotion,
the sole discoverer verifies itself, an outbound value lacks an approved
requirements derivation, an `unknown` source time is represented as current, a
partial terminal outcome exposes a selectable lead, a lead starts Tailor, or a
provider/verification failure silently falls back.
