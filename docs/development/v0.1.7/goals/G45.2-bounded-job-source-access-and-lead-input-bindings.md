# G45.2 — Bounded Exa Research and Lead Input Bindings

**Version:** v0.1.7
**Status:** Proposed — contract defined; not activated
**Depends on:** G43.2, G45, and S45.2 Adopt decision
**First consumer:** G46.2 `find-jobs-for-requirements`

## Outcome

G45.2 gives an operator-started Find Run a bounded, provider-accounted Exa
research capability. The selected agents do the research: a Codex participant
develops the search, and a Claude participant independently checks coverage,
citations, and lead evidence. GigAI mediates every Exa action against the
sealed Plan rather than expecting an operator to browse job sites manually.

```text
requirements profile + approved Exa research policy
  -> sealed role assignments, query brief, and research budget
  -> direct Run confirmation
  -> Codex research actions + Claude independent research/verification
  -> private Exa snapshots, citations, normalized leads, and report
  -> operator selects LEAD_ID
  -> idempotent lead-to-job-description binding
```

The operator starts the foreground Run and may select a resulting lead. They
do not need to manually find the leads. G45.2 is not a generic crawler,
browser, search engine, credential store, job-board login, application tracker,
scheduler, or unrestricted model-tool facility.

## Exa research capability boundary

`exa-research-policy.schema.json` has schema ID
`urn:gigai:schema:exa-research-policy:1`. Its strict, reviewed policy requires
`schema_version`, `policy_id`, `provider_id`, `provider_api_version`,
`capability_id`, `permitted_actions`, `query_field_mapping`, `limits`,
`usage_cost_rule`, `citation_normalization`, `fixture_replay_identity`, and
`created_at`. `policy_id` matches `exa_policy_<uuidv4>`; `provider_id` is
exactly `exa`; and `permitted_actions` is a non-empty subset of `search` and
`contents`. It names the Exa provider/API version, capability ID, permitted
search/content action kinds, allowed requirements-to-query field mapping,
response limits, usage/cost accounting rule, citation normalization rule, and
sanitized fixture/replay identity. It contains no API key, credential value,
user-private source text, or arbitrary HTTP template.

The policy permits only Exa `search` and `contents` actions. GigAI sends those
actions to the configured Exa credential reference held in machine
configuration; the reference is never a portable artifact, workpad artifact,
or diagnostic value. There is no direct HTTP fetch of a result URL, browser
session, cookie, JavaScript execution, or raw model-supplied URL. Result URLs
are provenance/citation data only.

S45.2 selects one reviewed Exa policy. Until it records an Adopt decision,
every attempted G45.2 operation fails `research_provider_not_approved`. A
missing, unusable, or unaccountable Exa configuration fails
`research_provider_unavailable`, `research_credential_unavailable`, or
`research_usage_unavailable` before an Exa action. There is no web, model, or
source-provider fallback.

The policy's hard maximums per Run are:

- 8 Exa `search` actions;
- 24 Exa `contents` actions;
- 10 results returned by one search action;
- 40 distinct source documents represented in the Run;
- 2 MiB provider response bytes per action and 12 MiB aggregate; and
- the Plan's declared Exa cost and wall-time ceilings.

The policy may lower but never raise these values. Provider-reported usage/cost
is recorded for every action; a reviewed derivation table may be used only when
the provider cannot report cost. Usage and cost must be available before an
action is accepted, under G43's applicable accounting policy.

For the private G46.2 UAT, `standard@1` requires two distinct usable configured
targets: a Codex CLI target performs the primary research role and may consume
at most 5 searches and 15 contents actions; a Claude Code target performs the
independent research/verification role and may consume at most 3 searches and
9 contents actions. The G43 verifier, adjudicator, and resolver then process
the sealed evidence under their existing role rules. This is multi-model
research and review, not a claim that every later verifier target is distinct.
There is no target substitution, role reassignment, or budget transfer on
failure.

An agent may request a typed `exa_search` or `exa_contents` action only with
the sealed requirements locator, action parameters, and declared research
reason. GigAI validates the action type, caller role, remaining role/Run budget,
query field mapping, and requested Exa result IDs before executing it. The
returned response becomes a private immutable snapshot. Fetched text is
untrusted data, explicitly delimited as evidence in every agent input: it
cannot alter the Gig, graph, Plan, budget, capability, provider, source scope,
prompt, or later command.

## CLI contract

G45.2 adds only explicit, bounded surfaces:

```text
gigai research providers [--json]
gigai research policy show exa [--json]
gigai job-requirements add --research-provider exa (--file PATH | --stdin)
  [--label LABEL] [--target PATH]
gigai job-lead select LEAD_ID --gig GIG_ID --confirm [--target PATH]
```

Listing or inspecting policy performs no provider request. Adding requirements
writes one private immutable input record and performs no model or Exa action.
`run-plan create` receives the requirements-input ID and `exa` policy ID
explicitly, renders the query brief, allowed action kinds, participant mapping,
and all research ceilings in the sealed Plan, and still performs no research.
Only the later direct-confirmed Find Run may mediate Exa actions. Human/JSON
output follows the existing safe-label/ID/digest boundary.

## Immutable research, citation, and lead records

Each mediated action writes a private `exa-research-action.schema.json` record,
schema ID `urn:gigai:schema:exa-research-action:1`, under
`runs/<run_id>/research/actions/action_<uuidv4>.json`. It requires
`schema_version`, `action_id`, `run_id`, `gig_id`, `graph_id`, `participant`,
`action_kind`, `requirements_refs`, `request_digest`, `response`, `citations`,
`usage`, `created_at`, and `status`. `action_kind` is exactly `search` or
`contents`; `status` is `complete`, `no_results`, `blocked`, or `failed`.
`response` and every citation snapshot are exact private artifact references.
The record stores the query/request digest and bounded safe query summary, not
the operator's private requirements text in diagnostics or committed evidence.

Normalized output is `job-lead-record.schema.json`, schema ID
`urn:gigai:schema:job-lead-record:1`, stored under
`runs/<run_id>/job-leads/lead_<uuidv4>/lead.json`. A record requires
`schema_version`, `lead_id`, `run_id`, `gig_id`, `graph_id`,
`research_actions`, `source_url`, `retrieved_at`, `as_of`, `citation_snapshot`,
`normalized_job_description`, `identity_key`, `relevance`, and `created_at`.
`research_actions`, `citation_snapshot`, and `normalized_job_description` are
exact artifact references. Every lead must cite at least one completed action
and one snapshot containing its displayed source facts.

`identity_key` is derived only from a provider-result public identifier or a
canonical public-field tuple defined by the policy. `relevance` contains only
requirements-reference locators, citation/source-field locators, and a bounded
explanation; it does not claim that the operator is qualified. Equal identity
keys within one Run deduplicate deterministically: the lowest canonical public
URL wins and remaining candidates remain deduplication evidence. Leads are
never silently merged or suppressed across Runs.

G45.2 also adds `urn:gigai:schema:run-input-record:2` without changing G45's
historical v1 record. v2 accepts sealed `job_search_requirements` inputs from
explicit operator paste or local text files, and sealed `job_description`
inputs with origin `lead_selection`. A requirements record contains only typed
query/filter fields allowed by the Exa policy: role/keywords, location/remote
preference, seniority, employment type, salary constraint where chosen, and
explicit include/exclude criteria. Résumé text, private work history, arbitrary
notes, and undeclared query fields are refused.

## Explicit lead selection and input binding

`gigai job-lead select LEAD_ID --gig GIG_ID --confirm` is the only operation
that creates a Tailor-eligible lead binding. It verifies the lead belongs to
the selected Job Search Lifecycle Gig and an approved
`find-jobs-for-requirements` Run, then writes a strict
`lead-input-binding.schema.json` artifact with schema ID
`urn:gigai:schema:lead-input-binding:1`.

The binding requires `schema_version`, `binding_id`, `project_id`, `gig_id`,
`lead`, `lead_snapshot`, `job_description_input`, `created_by`, and
`created_at`. `binding_id` matches `lead_binding_<uuidv4>`.
`lead_snapshot` is the exact normalized-job-description reference from the lead.
`job_description_input` is a new private
`urn:gigai:schema:run-input-record:2` record with kind `job_description` and
origin `lead_selection`; it records the exact lead reference and the same
snapshot digest. The enclosing binding then links that input record to its
lead-selection authority, avoiding a circular artifact reference. v1 G45
local-file/operator-paste inputs remain valid and unchanged.

The binding idempotency key is project ID, Gig ID, `lead_id`, and normalized
job-description digest. Repeating selection returns the existing binding. A
changed lead snapshot creates a new binding and a new input record. The command
writes private workpad evidence only: it does not start tailoring, allocate a
Run, invoke a model, grant research/provider permission, or alter application
state.

## Plan, consent, and privacy boundary

A Find Plan seals the requirements input, Exa policy, query brief, participant
assignments, action ceilings, provider-accounting rule, and citation policy.
Direct `gigai run --confirm` is the only authorization to invoke the selected
agents and mediate their Exa actions. A Tailor Plan may consume a lead-derived
job-description input only when the operator explicitly names the binding/input
ID; it seals the binding, lead, and exact job-description digest as sources. It
has its own direct Run consent.

Human and JSON output may show provider/policy ID, safe query summaries,
participant roles, action counts, safe public URL labels, retrieval time, lead
IDs, counts, and bounded relevance reasons. Raw Exa responses, private
requirements, local paths, cookies, credentials, and private source artifacts
remain out of portable packages, catalog fixtures, committed evidence, and
diagnostics. Sanitized fixtures contain no live applicant or job-source data.

## Acceptance evidence

G45.2 requires deterministic Exa action fixtures plus one operator-consented
live Exa execution after S45.2 Adopt. It proves:

- no Exa action can run before direct Run confirmation or outside its exact
  Codex/Claude role assignment, policy, query fields, result IDs, and budget;
- unavailable credential/accounting, unsupported action, over-budget action,
  malformed action, malformed response, provider failure, and cancellation
  fail honestly with no fallback;
- the sealed query brief lists exactly outbound fields and excludes résumé,
  private work history, and surrounding conversation;
- every result/lead has reconstructable action, usage, citation, provider,
  retrieval-time, source-URL, and snapshot provenance;
- an Exa fixture containing instructions, credential requests, or capability
  claims is retained as untrusted evidence and cannot change a later action or
  command;
- the Claude role independently verifies the Codex research evidence and a
  missing/contradicted citation cannot become a surfaced lead;
- no-match, stale content, duplicate leads, and partial provider failure have
  typed terminal outcomes; and
- lead selection is direct-confirmed, idempotent, digest-bound, does not start
  tailoring, and creates an input binding consumable only by an explicitly
  sealed Tailor Plan.

## Out of scope and stop conditions

Out of scope: arbitrary URL fetches, direct browser/web-search control, HTML
scraping, JavaScript, login/cookies, job application submission, outreach,
mutable saved/applied states, cross-Run lead suppression, schedules, and
provider-led capability or policy selection.

Stop if an agent can invoke Exa outside its sealed role/budget, Exa is called
without direct Run confirmation, a raw result URL is fetched directly, a
result is treated as instruction, a lead is selected without direct operator
confirmation, a binding starts tailoring or grants consent, private data enters
a package/committed evidence, or a failure triggers fallback.
