## Design choices

- **Dependency set**: exactly `react` 19.3.0, `react-dom` 19.3.0 as
  dependencies; `vite` 8.3.0, `@vitejs/plugin-react` 6.1.1 as devDependencies
  — all four pinned to exact versions (no `^`/`~`), confirmed by the
  `grep -c` check above. No router, state, or CSS library, per the SHELL
  instruction (a one-page app doesn't need one). Versions were the current
  npm registry latest as of this run (`npm view <pkg> version`), and
  `@vitejs/plugin-react@6.1.1` explicitly supports `vite@^8.0.0`; Node
  v26.7.0 in this environment satisfies vite 8's `node: ^20.19.0 || >=22.12.0`
  engine requirement.
- **`api.js`** is the sole place issuing `fetch`. It:
  - Builds `UIConsentEnvelope` with all fixed fields exactly as frozen in
    `scout_find_jobs_contracts.py:1565-1585` (`schema_version: "1.0"`,
    `kind: "operator_run_consent"`, `action: "run"`,
    `actor: {kind: "operator", id: "local-user"}`,
    `source: "direct_local_ui_confirm"`), generating only `invocation_id`
    and `occurrence_id` via `crypto.randomUUID()`.
  - Builds the full `RunRequest` body (`schema_version:
    "scout-find-jobs-run-request:1"`, `consent`, `config_digest`,
    `selection_cap`, `selection_rule: "new_or_edited_role_match"`
    — contracts' only `SelectionRule` member — `model_target`), matching
    `RunRequest` at `scout_find_jobs_contracts.py:1621-1638`.
  - Maps HTTP status to plain-language messages: 400/422 "malformed/rejected,
    reload and try again", 403 "consent missing/stale/target not allowed",
    404 "run not found", 409 "config changed since loaded, reload" (and the
    UI auto-reloads config on a 409 from `/api/run`, per the task's explicit
    409 instruction), 504 "server timed out, may still be running, check
    status again". A network-level fetch failure (status 0) gets its own
    "could not reach the local API" message. Note `/api/run`'s frozen
    `status_codes` tuple (`ROUTES` at line 1732) is `(202, 400, 403, 409,
    422)` and does not list 504; I still map 504 defensively since the task
    explicitly asked for it and a reverse proxy/timeout could still produce
    one even if the route spec doesn't declare it as a normal response.
  - `getConfig`/`startRun`/`getRunStatus`/`getRunResults` map 1:1 onto the
    four `ROUTES` entries (`GET /api/config`, `POST /api/run`,
    `GET /api/runs/{run_id}`, `GET /api/runs/{run_id}/results`).
- **Config screen** (`ConfigPanel.jsx`): renders roles, merged queries,
  location/remote, published_after, per-source toggle tags, default cap,
  default model target, and the resume preview. When
  `config_response.resume_preview` is `null` (per `ConfigResponse` at
  line 1603-1618, which allows `None`), it shows the exact operator command
  from the task (`gigai reference add --kind resume ...`) and the "Run
  workflow" button is disabled (`App.jsx`'s `canRun = Boolean(configResponse)
  && hasResume`).
- **Confirm dialog** (`RunConfirmDialog.jsx`): shows sources, queries, role
  filter as read-only text; a number input for cap (min 1, max 50, seeded
  from `default_assess_cap`, matching `RunRequest.selection_cap`'s
  1-50 contract bound at line 1638); a select for `model_target` with
  exactly the three `ModelTarget` enum values (`ollama_local`, `codex_cli`,
  `openrouter_api`); and a warning that acquisition uses the network, with
  the wording changing to explicitly call out posting/resume text going to
  the provider when a non-`ollama_local` target is selected. Confirm is
  disabled while the cap is out of `[1, 50]` or while a request is in
  flight.
- **Run status** (`NodeStatusList.jsx`): shows all three fixed node slugs
  (`acquire`, `assess`, `present` — the graph's only nodes per the roadmap)
  with each one's own `NodeReceipt.status` (defaulting to "pending" if no
  receipt exists yet) plus the aggregate `RunStatusResponse.status`.
  `App.jsx` polls `GET /api/runs/{id}` every 2000ms via `setTimeout`
  (chosen over `setInterval` so a slow response can't pile up overlapping
  requests) and stops once `status` is one of the terminal `AggregateStatus`
  values (`succeeded`, `failed`, `blocked`, `cancelled`, `interrupted` —
  everything in that enum except `pending`/`running`, matching the frozen
  precedence in `aggregate_status()`), then fetches results once.
- **Results** (`ResultsView.jsx` + `AssessmentCard.jsx` + `MatrixBadge.jsx`):
  pinned resume block (only rendered if non-null); a postings table
  (title/company/location/source/outcome) from `payload.rows`
  (`PostingRowResult`); one expandable `<details>` card per
  `payload.assessments` entry showing the requirements × evidence × status
  matrix with `met`/`partial`/`gap` colored badges (green/amber/red),
  suggestions, and questions; a not-assessed list translating each
  `NotAssessedReason` enum value into a human sentence (all 8 canonical
  reasons from `NotAssessedReason` at line 143-157 are covered, not just the
  compatibility aliases); and a redacted failures section listing
  `source_kind`/`query_key`/`message` only (never a raw response body, since
  `FailureRow` itself is already redacted by the acquire side per contracts'
  own docstring — this screen just renders what it's given).
- Verified field/shape choices against `fixture-api-config-response-v1.json`,
  `fixture-api-run-request-v1.json`, `fixture-api-run-response-v1.json`,
  `fixture-api-run-status-response-v1.json`,
  `fixture-api-run-results-response-v1.json`, and
  `fixture-present-payload-v1.json` (which exercises `interrupted` status,
  a `model_unavailable` assess failure, an `over_cap` not-assessed reason,
  and a redacted ATS failure — all rendered correctly by manual trace
  through the components' logic).
