Scout CLI reference

44 commands (schema v1). Agents: run gigai agent-context --json for the machine-readable form.

  • effect: read never changes state; write may change GigAI state or files (for some commands only with certain options).
  • external: the strongest thing the command can reach. none is offline, model may call a model provider (cost, and text leaves this machine), network may make other network requests.

gigai scout answer

Section titled “gigai scout answer”

Answer one question once; the answer is reused across every posting and profile.

gigai scout answer [OPTIONS] QUESTION_ID

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {ok, schema_version, record_id, revision_id, question_id, answer, reassessed}.

Example:

The answer is the user’s (0.1.10.7: not one profile’s) and is reused by every later assessment, also when a posting words the question differently. –question keeps the question’s own words with it; –actor agent records that an agent wrote it; –revision (the revision you read) refuses the write with revision_conflict when the answer changed since. An answer holding an email, phone, link or street address is refused (personal_info_refused). –reassess JOB_URL_OR_ID re-runs the assessment with a model (external=model). The same body as POST /api/answers. 0.1.10.7: a saved answer queues the pipeline (tailored resume, assessment against it, Scout ATS score, Scout label) for every job of an active profile whose assessment left that question open: at most pipeline.auto_jobs_per_trigger (10) run, the rest wait for an approval (gigai scout pipeline approvals). –json then carries pipeline {trigger, state, enqueued, awaiting_approval, unchanged, skipped, approval}: ids, codes and counts. The Scout server runs the queued jobs; without it, gigai scout new –process does.

gigai scout answers delete

Section titled “gigai scout answers delete”

Remove an answer.

gigai scout answers delete [OPTIONS] QUESTION_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, deleted}.

Example:

Needs –confirm. The answer is never listed, offered or sent to a model again; the project’s journal keeps the older revision of the record it was in. With –revision (the value you read) the delete is refused with revision_conflict when the answer changed since. The same body as DELETE /api/answers/{question_id}.

gigai scout answers list

Section titled “gigai scout answers list”

List the user’s answers: every answered question, with its tag and the jobs that asked or reused it.

gigai scout answers list [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, answers, total, tags}.

Example:

Answers belong to the user, not to a profile. Each answer carries question_id, question, answer, tag, jobs (kind answered | confirmed | reused), written_by (operator | agent), created_at, updated_at, revision and history. The same body as GET /api/answers.

gigai scout answers migrate

Section titled “gigai scout answers migrate”

Move the 0.1.10.5 per-profile story bank to user-level answers (once).

gigai scout answers migrate [OPTIONS]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, migrated, answers, merged, conflicts, profiles, first_run}.

Example:

Every read and write does this by itself the first time; this command does it now and prints the counts. Every profile’s answers become the user’s. Two profiles that answered the same question: the newest write is the answer; merged counts the ones that said the same, conflicts the ones that differed (the other text is kept in the answer’s history and stays in the journal). The old file is kept as story_bank/bank.v1.json. A second run changes nothing and counts 0 (migrated: false; first_run holds the first run’s counts).

gigai scout answers save

Section titled “gigai scout answers save”

Save an answer: a new one, or a change to its text, question words and/or tag.

gigai scout answers save [OPTIONS] QUESTION_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, answer}.

Example:

Local, no model call. A new QUESTION_ID needs the answer; an existing one takes whatever is given. Every write bumps the answer’s revision and records who wrote it (–actor). Pass –revision (the revision you read with show –json) to be safe against a concurrent write: when the answer changed since, the save is refused with revision_conflict and –json carries the current answer. An empty –tag puts the automatic tag back. Text holding an email, phone, link or street address is refused (personal_info_refused). The same answer object as POST /api/answers and PUT /api/answers/{question_id}. 0.1.10.7: a saved answer (not a tag alone) queues the pipeline (tailored resume, assessment against it, Scout ATS score, Scout label) for every job of an active profile whose assessment left that question open: at most pipeline.auto_jobs_per_trigger (10) run, the rest wait for an approval (gigai scout pipeline approvals). –json then carries pipeline {trigger, state, enqueued, awaiting_approval, unchanged, skipped, approval}: ids, codes and counts. The Scout server runs the queued jobs; without it, gigai scout new –process does.

QUESTION_ID is the answer’s id from list. Read revision from here before a save or delete with –revision. The same body as GET /api/answers/{question_id}.

gigai scout jobs assess

Section titled “gigai scout jobs assess”

Assess these postings: ask first (count and estimate), assess on approval.

gigai scout jobs assess [OPTIONS] [JOBS]...

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {schema_version, status, checked_at, question, counts, not_found, approval, assessed, postings, profiles} (what POST /api/postings/assess answers).

Example:

JOBS are posting URLs; without them the filter (–query, –state, –window, as gigai scout jobs list) selects the postings. What a run’s assess step did, without a run. Nothing is assessed without approval: without –yes the answer is status ask with the count per profile and the estimate from the recorded model calls, and no model call is made; in a terminal the command then asks and waits for y or n. –yes approves: the batch is recorded (approval: its id, who approved with –actor, how many) and each posting is assessed for the profile it fits best (or –profile), one model call each, from the posting text already stored (nothing is fetched). While a batch runs the pipeline and the rank lane start nothing, and a second batch is refused (assess_batch_running). A posting whose assessment is current is left out unless –again. status is then assessed (assessed.failed lists what could not be assessed, by error code) or nothing_to_assess. NO OUTPUT MIXES: posting text only, nothing you wrote.

gigai scout jobs import-runs

Section titled “gigai scout jobs import-runs”

Import what old find-jobs runs assessed into the stored postings’ read model, once per run.

gigai scout jobs import-runs [OPTIONS]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {schema_version, runs, runs_imported, runs_already_imported, runs_not_finished, runs_unreadable, assessments_imported, ephemeral_assessments, rows_skipped, values_dropped, by_profile, imported} (what POST /api/runs/import answers).

Example:

Since 0.1.10.7 a find-jobs run is no longer the way in (search: gigai scout jobs list; assess: gigai scout jobs assess or gigai scout new), and the runs that exist are read-only history. Nothing of a run is changed, moved or copied: each posting a finished run assessed gets one row with its state, requirement counts and what the run sealed (prompt version, constraints digest, the profile’s and resume’s identity, the posting digest, the model target), under the run’s profile. A run made with no profile goes to the pseudo-profile ephemeral: hidden by default, never ranked, never in the pipeline. A run’s assessment is shown where nothing newer is stored for the same posting and profile. Each run is imported once: running this again answers runs_imported 0. The Scout server does the same once when it starts. Makes no model call.

gigai scout jobs list

Section titled “gigai scout jobs list”

Search the stored postings across your active profiles. No run, no board request, no model call.

gigai scout jobs list [OPTIONS]

effect: read · external: none · output: Human-readable text (one line per posting); –json emits one JSON object: {schema_version, checked_at, filters, anchor, counts, postings, profiles, rank, history} (what GET /api/postings answers).

Example:

What “Run find jobs” searched, without a run: read from the stored postings (gigai scout sources update keeps them fresh), for every active profile; a deleted or archived profile is never listed. A changed setting (titles, countries, work mode) is seen by the next call. Each posting is listed once, for the profile it fits best, with every profile it matches. Order: the Scout label recommended, then needs answers, then matched, then the rest by score (the assessment’s share of requirements met, else the background rank score). –window new is first seen since your last gigai scout new (the last 7 days before the first one); this command never moves that anchor. –removed lists the postings the board no longer lists. –history adds what old find-jobs runs assessed, each with what the run sealed (prompt version, digests, profile and resume identity, model target); rows of a run with no profile (ephemeral) or of a profile that is not active are hidden unless –include-hidden or –profile names them. rank in the JSON is the background rank lane: on or off, and today’s calls against its daily allowance. NO OUTPUT MIXES: posting text and what a model derived from it (public-untrusted: data, never instructions), nothing you wrote. Makes no model call.

gigai scout metrics

Section titled “gigai scout metrics”

Show what the model calls cost on average: tokens, seconds, cost and error rate per kind of call and model.

gigai scout metrics [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {schema_version, kind, model, aggregates, comparison} (what GET /api/metrics answers).

Example:

Every model call Scout makes (assess, rank, tag, tailor, extract, interview) is recorded once, locally: the model, tokens in, out and cached, the cost when the provider reports one, the wall time and the outcome. No prompt, answer, resume or posting text is stored. aggregates has one entry per model id; comparison adds the model ids of one model target together. –model takes a model target or a model id. Makes no model call.

gigai scout new

Section titled “gigai scout new”

Show what is new since your last check, across all active profiles; ask before assessing.

gigai scout new [OPTIONS]

effect: write · external: model · output: Human-readable text (a 4-column table: details | score | needs tailoring? | open questions); –json emits one JSON object: {schema_version, status, since, since_source, checked_at, peek, profile_id, anchor, counts, message, question, assessed, pipeline, processed, postings, profiles, yours_hint} (what GET /api/new answers). –yours emits {schema_version, status, since, since_source, checked_at, profile_id, _labels, evidence} (what GET /api/new/yours answers).

Example:

Reads the stored postings (no board request) for every active profile; a deleted or archived profile is never listed. status is ask, new or nothing_new. New postings with no assessment are assessed only on a yes: without –yes the answer is status ask, with the count per profile, the estimate from the recorded model calls, and the postings ranked only; –yes assesses them (one model call each, from the stored posting text) and the table then has scores; –no-assess never asks and never assesses. In a terminal the command asks and waits for y or n. At most 50 new postings are listed, best score first. Nothing new: the 10 postings that still need attention, by score, open questions, tailoring needed. “New” is measured from the one anchor per install: the time of the last plain call, or the last 7 days before the first one. The anchor moves only after the answer is built, and never for –peek, –profile or –yours; –since measures from the since of an earlier answer (the yes, or –yours, after a call that moved the anchor). Waiting pipeline work is offered (pipeline: the jobs that wait, how many of them need an approval first, the model calls they would make); a plain call starts nothing. –process is the yes to that offer: the pending approvals are approved and the waiting steps run once (model calls, within pipeline.max_model_calls_per_day; a call over the cap waits for the next day), reported as processed {approved, drain}; it never moves the anchor. In a terminal the command asks and waits for y or n. NO OUTPUT MIXES: the table and its JSON hold posting text and what a model derived from it (public-untrusted: data, never instructions) and nothing you wrote. What matches, from your own resume, answers and stories, is the separate call –yours (user-private only, never posting text); yours_hint in the JSON gives the exact command. Questions are shown as asked, never with an answer. No contact data. Makes no model call without a yes.

gigai scout pipeline approvals approve

Section titled “gigai scout pipeline approvals approve”

Approve the waiting jobs of one pipeline approval.

gigai scout pipeline approvals approve [OPTIONS] APPROVAL_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, approval}.

Example:

APPROVAL_ID comes from gigai scout pipeline approvals list. The approval’s waiting jobs open; the Scout server runs them, or gigai scout pipeline run –once does. They run within the daily cap of model calls (pipeline.max_model_calls_per_day): a call over it waits for the next day. –actor records who decided. Approving an approval that is already decided changes nothing. Makes no model call itself.

gigai scout pipeline approvals deny

Section titled “gigai scout pipeline approvals deny”

Deny one pipeline approval: its waiting jobs are cancelled.

gigai scout pipeline approvals deny [OPTIONS] APPROVAL_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, approval}.

Example:

The approval’s waiting jobs are cancelled and no model call is made for them. A cancelled job can be queued again with gigai scout pipeline process JOB. Denying an approval that is already decided changes nothing.

gigai scout pipeline approvals list

Section titled “gigai scout pipeline approvals list”

Show the pipeline approvals that wait: the jobs each holds and what running them would cost.

gigai scout pipeline approvals list [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {schema_version, pending, approvals} (what GET /api/pipeline/approvals answers).

Example:

One trigger (a saved answer or story, a changed profile) queues at most pipeline.auto_jobs_per_trigger jobs (10); the rest wait in one approval and nothing of theirs runs until it is approved. Each approval: its id, the trigger, how many jobs it held and how many still wait (with each job’s link and profile), the model calls they would make and, when the recorded calls can say, the tokens. Ids, codes and counts only: no posting, resume or answer text. –all also lists the approvals already approved or denied. Makes no model call.

gigai scout pipeline cancel

Section titled “gigai scout pipeline cancel”

Cancel a job’s waiting pipeline steps.

gigai scout pipeline cancel [OPTIONS] JOB

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, action, profile_id, job, steps}.

gigai scout pipeline process

Section titled “gigai scout pipeline process”

Put one assessed job through the pipeline now: tailored resume, assessment against it, Scout ATS score, Scout label.

gigai scout pipeline process [OPTIONS] JOB

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {enqueue, drain, status}.

Example:

JOB is the posting URL of a job this profile already has an assessment for; the posting is read from that assessment, nothing is fetched. Steps: tailor (from the profile’s resume, your answers and the stories that match the posting; no contact data), then the assessment against the tailored resume (stored beside the job’s assessment, which stays the job’s verdict) and the Scout ATS score, then the Scout label. The Scout label is Scout’s own suggestion from your settings, resume and answers, not a prediction of what an employer will decide. Running it again with nothing changed makes no model call; –force tailors again. A tailored resume that is yours (tailored on demand, or with a line you chose or edited) is never replaced, not even with –force: the tailor step keeps it (tailor_kept_user_edits in the drain’s step and in status.outputs.tailored_resume.outcome), calls no model, and the assessment, the Scout ATS score and the Scout label are made against it. At most two model steps (tailor, assess), each counted against pipeline.max_model_calls_per_day (40): a call over the cap waits for the next day, it does not fail. Waits while a find-jobs run, an assess batch or a manual sources update is running. Naming a job is an explicit choice: the per-trigger cap does not apply, and a job waiting for an approval is taken out of it and run.

gigai scout pipeline rank

Section titled “gigai scout pipeline rank”

Rank the stored postings your active profiles match that have no rank score yet, without the Scout server.

gigai scout pipeline rank [OPTIONS]

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {schema_version, state, reason, calls, ranked, warning, retry_at, profiles, calls_today}.

Example:

The Scout server ranks in the background while it is open (a few calls at a time); this is for use without it. One model call ranks up to 50 postings, newest first, for each active profile; a deleted or archived profile is never ranked. The score is kept per posting, resume, settings and model, so a posting ranked once is not ranked again until one of those changes. All profiles share one daily allowance: rank.max_calls_per_day (100) and the warning level rank.warn_calls_per_day (60), in the project’s settings file. A call past the warning level is made and warning is true; the call that would go over the maximum is not made: state is waiting (daily_cap_reached) and retry_at is the next local day. Other states: ran, idle (nothing to rank), yielded (a sources update, an assess batch or a find-jobs run is running), busy_elsewhere (the server is ranking now), disabled (rank.max_calls_per_day is 0, or the settings file cannot be read), unavailable (no usable model, or an answer that could not be read). Ids, counts and codes only: no posting or resume text.

Open a job’s failed or cancelled pipeline steps again.

gigai scout pipeline retry [OPTIONS] JOB

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, action, profile_id, job, steps}.

Example:

JOB is the posting URL. The steps are opened with the inputs they had; the Scout server, or gigai scout pipeline run –once, then runs them. Makes no model call itself.

gigai scout pipeline run

Section titled “gigai scout pipeline run”

Run the pipeline’s waiting steps once, without the Scout server.

gigai scout pipeline run [OPTIONS]

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {schema_version, state, reason, steps, model_calls}.

Example:

The Scout server runs the pipeline by itself while it is open; this is for use without it. Safe to run while the server is up: both claim steps from the same local queue, so no step runs twice. state is ran, idle (nothing to run), yielded (a find-jobs run, an assess batch or a manual sources update is running; reason names it), or disabled (pipeline.enabled is off, or the settings file cannot be read). Model calls count against pipeline.max_model_calls_per_day; a step over the cap waits for the next day.

gigai scout pipeline status

Section titled “gigai scout pipeline status”

Show each job’s pipeline steps, why a step waits, and today’s model calls against the cap.

gigai scout pipeline status [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {schema_version, setting, counts, calls_today, lanes, yielding_to, steps} and, with –job, {runs, outputs}.

Example:

Ids, states, codes, numbers and file paths only: no posting, resume or answer text. A waiting step says why: daily_cap_reached, retry_backoff or lane_backoff. With –job: each attempt’s model, tokens, time and outcome (runs), and what is stored for the job (outputs: the base and the tailored assessment’s verdict and share of requirements met, the tailored resume’s path, the Scout ATS score, the Scout label). Makes no model call.

gigai scout privacy

Section titled “gigai scout privacy”

Show what the one-time contact cleanup removed (running it first if it has not run).

gigai scout privacy [OPTIONS]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, status, removed_any, display_settings, resumes, history_note, shown, text}.

Example:

Counts only, never a value. The first run after an upgrade from before 0.1.10.7 removes the name and contact lines from stored resumes (a clean revision through the normal write path; profiles re-pointed) and the saved name and contact items from the PDF settings. Earlier copies remain in the workpad’s local history; this does not rewrite it. Safe to rerun: an already cleaned workpad is not touched again.

gigai scout profile delete

Section titled “gigai scout profile delete”

Delete a profile: it stops showing and searching; its history stays.

gigai scout profile delete [OPTIONS] PROFILE_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object.

Example:

The profile leaves the profile list, the switcher, new runs and background tagging; its runs and assessments stay readable (hidden from the default Jobs list) and the answers and stories (the user’s, not the profile’s) are untouched. The default profile and the only active profile are refused. Deleting the selected profile selects the default profile.

gigai scout resume add

Section titled “gigai scout resume add”

Import a file as the resume reference and create the record find-jobs reads.

gigai scout resume add [OPTIONS] FILE

effect: write · external: none · output: Human-readable text; –json emits one JSON object.

Example:

Works as the very first command on a fresh machine: writes the default GigAI settings (like ‘gigai scout run’), installs Scout if needed, then imports the file. Never rewrites an existing config. The name and contact lines (email, phone, address, links) are removed and discarded before the resume is stored; –json carries contact_removed {removed: {kind: count}, message} (null when there were none).

gigai scout resume pdf

Section titled “gigai scout resume pdf”

Render a resume to PDF locally: your own markdown, or a stored tailored resume.

gigai scout resume pdf [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {ok, out_path, source, pages, bytes, spacing_scale, header, finish_url, scout_running}.

Example:

No model call and no network: the markdown is only rendered, never stored. –in takes resume markdown in GigAI’s format (## Summary, ## Experience with ### entries and - bullets, ## Skills, ## Education, ## Projects, ## Other; trailing comments are dropped), so the markdown of a tailored resume renders as it is. The PDF has no header (no name or contact line; a blank block keeps the page layout): finish_url is the local Scout page (#/pdf) where the person types their details in the Generate PDF form and downloads; an agent cannot finish that step unless it drives that person’s browser. –spacing (0.7-1.4) and –auto-fit/–no-auto-fit change the layout for this render only; –spacing alone turns auto fit off. Writes only the PDF: –out, else --.pdf (resume-.pdf for –in) in the current folder. To change two bullets and render: edit the two lines in the markdown file and run the first example; for a stored tailored resume, change the lines with PUT /api/tailored-resumes/lines (use: custom) and run the –tailored example.

effect: write · external: none · output: Human-readable text; –json emits one JSON object.

Example:

gigai scout snapshot import

Section titled “gigai scout snapshot import”

Download the published metadata snapshot (postings, title tags, board validators; no descriptions) and add it to the stored company index.

gigai scout snapshot import [OPTIONS]

effect: write · external: network · output: Human-readable text; –json emits one JSON object.

Example:

Takes the full files, or only the delta when the stored snapshot is the delta’s base. Every file’s SHA-256 is checked before it is read. A board checked on this machine at or after the snapshot is left alone, and nothing local is deleted except boards the snapshot itself added and later lists as removed. Unreachable or not published is a quiet no-op (exit 0); a snapshot that fails its checks or cannot be written exits 1 with the stored postings unchanged. Makes no request when the snapshot.enabled setting (or GIGAI_SCOUT_SNAPSHOT=0) turns it off.

gigai scout story save

Section titled “gigai scout story save”

Save a story: a new one, or a change to the given fields of an existing one.

gigai scout story save [OPTIONS] [STORY_ID]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, story}.

Example:

Local, no model call. A new story needs –title; its id is STORY_ID, else story:<the title’s first words> as the id normalizer writes them. For an existing STORY_ID only the given fields change (a given narrative part replaces that part; –tag and –answers replace the whole list). –file takes one JSON object with the fields of POST /api/stories (title, company, role, period, raw, narrative, tags, answers_questions, sources, and optionally story_id); the options override it. Pass –revision (the revision you read) to be safe against a concurrent write: revision_conflict, with the current story in –json. story_exists when a new story’s id is taken. Text holding an email, phone, link or street address in any field is refused (personal_info_refused). An assessment searches the stories for each job and puts only the few that match the posting into its prompt. The same story object as POST /api/stories and PUT /api/stories/{story_id}. 0.1.10.7: a saved story queues the pipeline for every job of an active profile whose assessment left open a question the story is about (at most pipeline.auto_jobs_per_trigger run, the rest wait for an approval); –json then carries pipeline {trigger, state, enqueued, awaiting_approval, unchanged, skipped, approval}.
