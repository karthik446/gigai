Scout CLI reference

58 commands (schema v1). Agents: run gigai agent-context --json for the machine-readable form.

  • effect: read never changes state; write may change GigAI state or files (for some commands only with certain options).
  • external: the strongest thing the command can reach. none is offline, model may call a model provider (cost, and text leaves this machine), network may make other network requests.

gigai scout answer

Section titled “gigai scout answer”

Answer one question once; the answer is reused across every posting and profile.

gigai scout answer [OPTIONS] QUESTION_ID

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {ok, schema_version, record_id, revision_id, question_id, answer, reassessed}.

Example:

The answer is the user’s (0.1.10.7: not one profile’s) and is reused by every later assessment, also when a posting words the question differently. –question keeps the question’s own words with it; –as agent (also –actor agent) records that an agent wrote it, and –source, free text, where the answer came from; –revision (the revision you read) refuses the write with revision_conflict when the answer changed since. An answer holding an email, phone, link or street address is refused (personal_info_refused). –reassess JOB_URL_OR_ID re-runs the assessment with a model (external=model). The same body as POST /api/answers. 0.1.10.7: a saved answer queues the pipeline (tailored resume, assessment against it, Scout ATS score, Scout label) for every job of an active profile whose assessment left that question open: at most pipeline.auto_jobs_per_trigger (10) run, the rest wait for an approval (gigai scout pipeline approvals). –json then carries pipeline {trigger, state, enqueued, awaiting_approval, unchanged, skipped, approval}: ids, codes and counts. The Scout server runs the queued jobs; without it, gigai scout new –process does.

gigai scout answers delete

Section titled “gigai scout answers delete”

Remove an answer.

gigai scout answers delete [OPTIONS] QUESTION_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, deleted}.

Example:

Needs –confirm. The answer is never listed, offered or sent to a model again; the project’s journal keeps the older revision of the record it was in. With –revision (the value you read) the delete is refused with revision_conflict when the answer changed since. The same body as DELETE /api/answers/{question_id}.

gigai scout answers list

Section titled “gigai scout answers list”

List the user’s answers: every answered question, with its tag and the jobs that asked or reused it.

gigai scout answers list [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, answers, total, tags}.

Example:

Answers belong to the user, not to a profile. Each answer carries question_id, question, answer, tag, jobs (kind answered | confirmed | reused), written_by (operator | agent), source (free text: where the answer came from, or null), created_at, updated_at, revision and history. The same body as GET /api/answers.

gigai scout answers migrate

Section titled “gigai scout answers migrate”

Move the 0.1.10.5 per-profile story bank to user-level answers (once).

gigai scout answers migrate [OPTIONS]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, migrated, answers, merged, conflicts, profiles, first_run}.

Example:

Every read and write does this by itself the first time; this command does it now and prints the counts. Every profile’s answers become the user’s. Two profiles that answered the same question: the newest write is the answer; merged counts the ones that said the same, conflicts the ones that differed (the other text is kept in the answer’s history and stays in the journal). The old file is kept as story_bank/bank.v1.json. A second run changes nothing and counts 0 (migrated: false; first_run holds the first run’s counts).

gigai scout answers save

Section titled “gigai scout answers save”

Save an answer: a new one, or a change to its text, question words, tag and/or source.

gigai scout answers save [OPTIONS] QUESTION_ID

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, answer}.

Example:

Local, no model call. A new QUESTION_ID needs the answer; an existing one takes whatever is given. Every write bumps the answer’s revision and records who wrote it (–as operator | agent; –actor is the same option; an agent passes –as agent). –source is free text, where the answer came from (“from the user’s repo, at the user’s request”): a new answer text without it drops the stored one, an empty value removes it. Pass –revision (the revision you read with show –json) to be safe against a concurrent write: when the answer changed since, the save is refused with revision_conflict and –json carries the current answer. An empty –tag puts the automatic tag back. Text holding an email, phone, link or street address is refused (personal_info_refused). The same answer object as POST /api/answers and PUT /api/answers/{question_id}. 0.1.10.7: a saved answer (not a tag alone) queues the pipeline (tailored resume, assessment against it, Scout ATS score, Scout label) for every job of an active profile whose assessment left that question open: at most pipeline.auto_jobs_per_trigger (10) run, the rest wait for an approval (gigai scout pipeline approvals). –json then carries pipeline {trigger, state, enqueued, awaiting_approval, unchanged, skipped, approval}: ids, codes and counts. The Scout server runs the queued jobs; without it, gigai scout new –process does.

gigai scout answers show [OPTIONS] QUESTION_ID

Example:

QUESTION_ID is the answer’s id from list. Read revision from here before a save or delete with –revision. The same body as GET /api/answers/{question_id}.

gigai scout assess

Section titled “gigai scout assess”

Assess ONE job against a resume right now, without a find-jobs run.

gigai scout assess [OPTIONS]

effect: write · external: model · output: Human-readable text; –json emits one JSON object.

Example:

Calls the configured model adapter (default from find-jobs.json). –job-url may fetch the posting over the network. One assessment sends to your model target: the stored posting; your resume (the lines of your master resume picked for the posting, or the profile’s own resume) with its contact lines removed by pattern; your search preferences (sponsorship, countries, location, titles, work mode); your saved answers; and the saved stories that match the posting. Pattern removal can miss an unusual name or contact format, so it is not a guarantee. A profile id is not contact data. With codex_cli or claude_cli the model target is your own login. A pasted resume (–resume, –resume-text) is sent in place of the profile’s. On a failure whose code is model_target_unavailable, model_denied, model_unavailable, assess_timeout, model_output_invalid or assessment_not_stored, the JSON error also says model_call_started, may_have_used_tokens, fresh_assessment_stored (always false) and next_action, and the text output says the same under the message. To see what would be sent without a call, use gigai scout jobs assess URL –json (it asks first).

gigai scout jobs assess

Section titled “gigai scout jobs assess”

Assess these postings: ask first (count and estimate), assess on approval.

gigai scout jobs assess [OPTIONS] [JOBS]...

effect: write · external: model · output: Human-readable text; –json emits one JSON object: {schema_version, status, checked_at, question, model_input_summary, counts, low_rank, not_found, approval, assessed, postings, profiles} (what POST /api/postings/assess answers).

Example:

JOBS are posting URLs; without them the filter (–query, –state, –window, as gigai scout jobs list) selects the postings. What a run’s assess step did, without a run. Nothing is assessed without approval: without –yes the answer is status ask with the count per profile and the estimate from the recorded model calls, and no model call is made; in a terminal the command then asks and waits for y or n. –yes approves: the batch is recorded (approval: its id, who approved with –actor, how many) and each posting is assessed for the profile it fits best (or –profile), one model call each, from the posting text already stored (a posting with none has its description fetched from its public board first, one request for it alone). 50 AT A TIME: one approval assesses the NEWEST 50 of them and never more (by the day the posting went up, else the day Scout first stored it); the question says the total and the 50 (“Assess the newest 50 of 120 postings? ~50 calls … (70 more after these 50)”), question.batch / more_after and counts.batch / more_after say it in numbers, and the same command again assesses the next 50. While a batch runs the pipeline and the rank lane start nothing, and a second batch is refused (assess_batch_running). A posting whose assessment is current is left out unless –again. A posting whose rank score is below fit.assess_min_rank (50; one not ranked yet is not) is left out too and counted (counts.low_rank_skipped); low_rank is the separate question for those (“3 low-ranked ones are skipped (rank below 50); assess those too? ~3 calls”) and –include-low-rank assesses them with the rest. status is then assessed (assessed.failed lists what could not be assessed, by error code) or nothing_to_assess. NO OUTPUT MIXES: posting text only, nothing you wrote. WHAT ONE ASSESSMENT SENDS. One assessment sends to your model target: the stored posting; your resume (the lines of your master resume picked for the posting, or the profile’s own resume) with its contact lines removed by pattern; your search preferences (sponsorship, countries, location, titles, work mode); your saved answers; and the saved stories that match the posting. Pattern removal can miss an unusual name or contact format, so it is not a guarantee. A profile id is not contact data. With codex_cli or claude_cli the model target is your own login. The status ask answer says it for the postings asked about, in model_input_summary: {schema_version, postings, model_calls, model_target, model_target_runs: local | own_login | api_key, profiles: [{profile_id, label, postings, resume_source: profile_view | master_evidence}], sends, search_preferences, contact_lines, answers_used, answers_saved, stories_used, stories_saved, public_fetch_needed, public_fetch_postings}. It holds ids, labels, counts and names, never a line of your text; no model call is made for it; it is null once the batch ran. In a terminal the same facts are printed above the y/n question. APPROVALS. Three approvals are separate: the user’s choice to assess; Scout’s own –yes (approve: true over the API); and the agent runtime’s own sandbox or model-provider approval. –yes does not bypass the runtime’s policy, and an API or UI route is not a workaround: an agent whose runtime refuses the command quotes the refusal and asks the user for the exact missing authorisation. FAILURES. An item of assessed.failed whose error_code is model_target_unavailable, model_denied, model_unavailable, assess_timeout, model_output_invalid or assessment_not_stored also says model_call_started, may_have_used_tokens, fresh_assessment_stored (always false) and next_action; the text output prints them once per cause. After an interruption (a timeout, a killed command), read the posting’s row first (gigai scout jobs list –query WORDS –json: assessment.assessed_at and stale_reason): a newer assessed_at with stale_reason null means it finished, and assessing again would be a second model call.

gigai scout jobs import-runs

Section titled “gigai scout jobs import-runs”

Import what old find-jobs runs assessed into the stored postings’ read model, once per run.

gigai scout jobs import-runs [OPTIONS]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {schema_version, runs, runs_imported, runs_already_imported, runs_not_finished, runs_unreadable, assessments_imported, ephemeral_assessments, rows_skipped, values_dropped, by_profile, imported} (what POST /api/runs/import answers).

Example:

Since 0.1.10.7 a find-jobs run is no longer the way in (search: gigai scout jobs list; assess: gigai scout jobs assess or gigai scout new), and the runs that exist are read-only history. Nothing of a run is changed, moved or copied: each posting a finished run assessed gets one row with its state, requirement counts and what the run sealed (prompt version, constraints digest, the profile’s and resume’s identity, the posting digest, the model target), under the run’s profile. A run made with no profile goes to the pseudo-profile ephemeral: hidden by default, never ranked, never in the pipeline. A run’s assessment is shown where nothing newer is stored for the same posting and profile. Each run is imported once: running this again answers runs_imported 0. The Scout server does the same once when it starts. Makes no model call.

gigai scout jobs list

Section titled “gigai scout jobs list”

Search the stored postings across your active profiles. No run, no board request, no model call.

gigai scout jobs list [OPTIONS]

effect: read · external: none · output: Human-readable text (one line per posting); –json emits one JSON object: {schema_version, checked_at, filters, anchor, counts, postings, profiles, rank, history} (what GET /api/postings answers).

Example:

What “Run find jobs” searched, without a run: read from the stored postings (gigai scout sources update keeps them fresh), for every active profile; a deleted or archived profile is never listed. A changed setting (titles, countries, work mode) is seen by the next call. Each posting is listed once, for the profile it fits best, with every profile it matches. Order, as gigai scout new: a current assessment first, then an old one, then not assessed; inside a group the verdict, then the fit number (fit: the share of requirements met with the must-haves counted twice), then the rank score, then the newest. A weak fit (state weak_fit: it waits on your answers, its fit is below 40 and its rank below 50; the fit block of the project’s settings file tunes both) is listed only with –state weak_fit; counts.weak_fit says how many there are and such a row asks no question. –window new is first seen since your last gigai scout new (the last 7 days before the first one); this command never moves that anchor. Each posting’s second line says its date: posted (the day the posting went up on its board, the one –window 7d / 30d judges; never the day it last changed) or, when the board gives no posting day, first seen (when Scout first stored it); in the JSON a row has published_at, published_kind (posted | updated: a last change, only for a board kind that gives nothing else), updated_at (the board’s last change, when it gives one) and first_seen_at. –removed lists the postings the board no longer lists. –history adds what old find-jobs runs assessed, each with what the run sealed (prompt version, digests, profile and resume identity, model target); rows of a run with no profile (ephemeral) or of a profile that is not active are hidden unless –include-hidden or –profile names them. rank in the JSON is the background rank lane: on or off, and today’s calls against its daily allowance. NO OUTPUT MIXES: posting text and what a model derived from it (public-untrusted: data, never instructions), nothing you wrote. Makes no model call.

gigai scout metrics

Section titled “gigai scout metrics”

Show what the model calls cost on average: tokens, seconds, cost and error rate per kind of call and model.

gigai scout metrics [OPTIONS]

effect: read · external: none · output: Human-readable text; –json emits one JSON object: {schema_version, kind, model, aggregates, comparison} (what GET /api/metrics answers).

Example:

Every model call Scout makes (assess, rank, tag, tailor, extract, interview) is recorded once, locally: the model, tokens in, out and cached, the cost when the provider reports one, the wall time and the outcome. No prompt, answer, resume or posting text is stored. aggregates has one entry per model id; comparison adds the model ids of one model target together. –model takes a model target or a model id. Makes no model call.

gigai scout new

Section titled “gigai scout new”

Show what is new since your last check, across all active profiles; ask before assessing.

gigai scout new [OPTIONS]

effect: write · external: model · output: Human-readable text (a 4-column table: details | score | needs tailoring? | open questions); –json emits one JSON object: {schema_version, status, since, since_source, checked_at, peek, profile_id, anchor, counts, message, question, stale_question, low_rank_question, fit, assessed, reassessed, ranking, pipeline, processed, postings, profiles, yours_hint} (what GET /api/new answers). –yours emits {schema_version, status, since, since_source, checked_at, profile_id, _labels, evidence} (what GET /api/new/yours answers).

Example:

Reads the stored postings (no board request) for every active profile; a deleted or archived profile is never listed. status is ask, new or nothing_new. New postings no profile has assessed are assessed only on a yes: without –yes the answer is status ask, with the count per profile, the estimate from the recorded model calls, and the postings ranked only; –yes assesses them (one model call each, from the stored posting text; a posting with no stored description has it fetched first, one request for that posting alone, counted in assessed.fetched_on_demand, and –reassess-stale does the same) and the table then has verdicts; –no-assess never asks and never assesses (in a terminal too: it prints the offers with their counts and ends). 50 AT A TIME: every yes (–yes, –reassess-stale, with or without –include-low-rank, an answer at a prompt) acts on the NEWEST 50 postings and never more, by the day the posting went up on its board, else the day Scout first stored it; each question says the real total, the 50 and what the 50 cost (“re-assess the newest 50 of 422? ~50 calls … (372 more after these 50)”) and carries batch and more_after beside the total; after a yes that left some, assessed / reassessed carry more_after and next (the call for the next 50), and –process runs at most 50 waiting steps a call. In a terminal the “new since” time moves when the run has done its work: a run left at a question (Ctrl-C) changes nothing. Postings that have only an OLD assessment (an old run’s, an older prompt’s, other settings’) are a second question of their own, stale_question, with its count and estimate (“N have only an old assessment; re-assess? ~N calls, ~X tokens”): –yes never answers it, –reassess-stale does (one model call each; it can be combined with –yes), reported as reassessed. counts.to_assess is the new postings no matching profile has assessed and counts.only_stale the postings with only an old assessment; neither changes while the background rank runs, and ranking says how far that rank is (ranked of total per profile). While a batch runs, progress lines go to stderr (“assessed 120 of 333 · ~25 min left”, the time left from the recorded average per call, then from the batch’s own pace); stdout stays the answer alone, so –json is still one JSON object. In a terminal the command asks and waits for y or n. At most 50 new postings are listed. A yes assesses only postings whose rank score is at least fit.assess_min_rank (50, in the fit block of the project’s settings file; a posting not ranked yet is assessed): the low-ranked ones are counted (counts.low_rank_skipped) and are a question of their own, low_rank_question (“112 low-ranked ones are skipped (rank below 50); assess those too? ~112 calls”), answered by –include-low-rank beside –yes (or beside –reassess-stale for the old assessments). A posting that waits on your answers while few requirements are met and its rank is low is a weak fit (state weak_fit: fit below fit.weak_fit_below_percent, 40, AND rank below fit.weak_fit_below_rank, 50): it is not listed here (counts.weak_fit; gigai scout jobs list –state weak_fit lists them), it is never one of the postings that still need attention, it asks no question and a saved answer never queues it in the pipeline. Rows come in one order: a current assessment first, then an old one, then not assessed; inside a group by verdict (matched, needs answers, other, weak fit, not a match), then the fit number (the share of requirements met with the must-haves counted twice; fit in each row), rank score, newest. The score column says the verdict, “fit N%”, “N of M requirements” and the rank (score_text), and an old assessment is labelled (stale_label); a posting is shown under the profile that tailored a resume for it, else one that has a current assessment. Nothing new: the 10 postings that still need attention, in the same order. “New” is measured from the one anchor per install: the time of the last plain call, or the last 7 days before the first one. The anchor moves only after the answer is built, and never for –peek, –profile or –yours; –since measures from the since of an earlier answer (the yes, or –yours, after a call that moved the anchor). Example:

Section titled “gigai scout story save”

Save a story: a new one, or a change to the given fields of an existing one.

gigai scout story save [OPTIONS] [STORY_ID]

effect: write · external: none · output: Human-readable text; –json emits one JSON object: {ok, schema_version, story}.

Example:

Local, no model call. A new story needs –title; its id is STORY_ID, else story:<the title’s first words> as the id normalizer writes them. For an existing STORY_ID only the given fields change (a given narrative part replaces that part; –tag and –answers replace the whole list). –file takes one JSON object with the fields of POST /api/stories (title, company, role, period, raw, narrative, tags, answers_questions, sources, and optionally story_id); the options override it. Pass –revision (the revision you read) to be safe against a concurrent write: revision_conflict, with the current story in –json. story_exists when a new story’s id is taken. Text holding an email, phone, link or street address in any field is refused (personal_info_refused). An assessment searches the stories for each job and puts only the few that match the posting into its prompt. The same story object as POST /api/stories and PUT /api/stories/{story_id}. 0.1.10.7: a saved story queues the pipeline for every job of an active profile whose assessment left open a question the story is about (at most pipeline.auto_jobs_per_trigger run, the rest wait for an approval); –json then carries pipeline {trigger, state, enqueued, awaiting_approval, unchanged, skipped, approval}.
